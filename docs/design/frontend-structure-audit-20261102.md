## 结论

现在最需要改的不是“再换一个组件库”，而是导航方式：**先选账号，再看这个账号的栏目；创建入口留在当前操作附近。** 当前代码把全部账号、全部栏目、创建表单放进同一条滚动列表，视觉稍作美化也不能解决“找不到刚才点了什么”。

建议第一阶段只调整账号导航、创建入口和对应布局。保留现有业务组件、API、聊天会话、素材和生产状态。无需整体重写前端，也无需为了细滚动条先安装 ScrollArea。

## 问题、证据与优先级

### P1：侧栏并没有按账号逐步展开

`web/src/pages/WorkspacePage.tsx:181–210` 无条件遍历全部账号，再遍历每个账号的全部栏目；`treeOpen`（41、179 行）只控制移动端整栏显示，不控制账号分组展开。没有导航搜索或过滤状态。

`web/src/pages/workspace.css:3` 给这份长列表设置独立滚动区域；10–14 行的栏目与账号行颜色、背景十分接近，也没有连接线或明确缩进。账号数量增长时，用户需要在一个越来越长的目录中找对象。

**建议：**账号切换器显示当前账号；打开切换器才列出/搜索其他账号。下面只展示当前账号的栏目。栏目多时，在这一层搜索；不要默认把其他账号的栏目也展开。账号概览继续能点击进入，当前栏目始终有明显选中态。未分配栏目保留明确入口，不静默丢失。

这比“全部展开的树加一根竖线”更能解决问题。需要保留一眼扫所有账号的能力时，可以在切换器中完成，不必把所有子栏目同时显示。

### P1：点击新建的地方和填写的地方分离

`WorkspacePage.tsx:193–194` 的账号行 `+` 只更新 `seriesDraft`；真正的栏目表单在整个账号列表之后的 212–222 行。新账号入口和表单又在 224–236 行。栏目多时，点击上方 `+`，表单却出现在很远的底部。源码能确定位置分离；是否发生自动滚动和实际焦点跳转需在浏览器验证，不能仅凭代码断言。

账号页头另有“新建栏目”（247 行），空状态又有一次（257 行）。多个触发点复用同一个底部表单，入口看似多，反馈位置却不明确。

**建议：**“新增账号”固定在账号切换器的可见位置；“新建栏目”在当前账号的栏目列表标题旁。两者打开就近的小表单或对话框，表单中显示所属账号，提交后定位新对象。不要把新建表单塞在全目录末尾。

### P1：空状态给出了错误的下一步

`WorkspacePage.tsx:255–258` 将“没有栏目”和“有栏目但没有选题”合并到同一个容器；虽然文案分开，按钮始终是“新建栏目”。有多个空栏目的用户会再次被引导创建栏目，而不是进入已有栏目添加第一条选题。

**建议：**无栏目 → 新建栏目；已有栏目无选题 → 显示已有栏目可进入，或引导在选定栏目中添加选题。不能把“没有内容”一概处理为“创建容器”。

### P2：导航被装在正文版心里，产生了不必要的横向空白

`web/src/components/Layout.tsx:45` 把整个工作区放入通用 `.page-container`。`web/src/styles.css:53` 为正文设置左右 24–56px、顶部 40px 内边距；`workspace.css:55–56` 再添加 260px 导航和 36px 栅格间距。

因此账号栏与主导航之间的空白来自**正文容器的 padding + 内层布局**，不是少用了某个 Tailwind 类。主导航、账号导航、正文三个区域的边界由两套布局拼在一起。

**建议：**工作台专属 frame 管理“账号导航 + 内容”两列，导航贴近主导航，正文单独获得内边距。不要修改全局 `.page-container` 来修这一页，否则 Run、Skill、Eval 页面也会受影响。窄屏保留现有可收起账号导航的能力。

### P2：组件已经存在，但公共控件仍是两套

`web/package.json` 只有 Radix Slot 依赖，没有 Tabs、ScrollArea 或 DropdownMenu 依赖；`web/src/components/ui/` 目前只有 Button、Input、Textarea 三个控件。`ui/README.md:14–18` 明确说明是按页面迁移，不是全站完成 shadcn 改造。

`web/src/styles.css:60–71` 保留 `.button` 变体；`ui/button.tsx:6–37` 另有本地 Button 变体。Workspace 仍使用原生 button、input、select 和旧类。两套共存是明确的迁移策略，本身不算错误；但继续各页面独立发明按钮间距、图标和危险动作，后续会不断出现“按钮对不齐”。

**建议：**只把本次会触及的导航操作、创建表单迁到现有公共控件；约定主要/次要/图标/危险动作的高度和间距。不要先迁遍所有页面，也不要把有复杂交互的图片查看器和聊天输入框一起替换。

### P2：样式补丁叠加，改一处时需要追多处覆盖

`workspace.css:2` 与 56 行重复定义栏宽和间距；25、61 行重复定义标题字号；30、76、82 行逐步覆盖添加表单；35、83、104 行分三次处理同一个 760px 断点。`styles.css:18–24` 又全局修改原生 details/summary 的外观。

这些规则不证明页面一定有 bug，但说明布局规则不是由一个清楚的组件负责；改导航密度、移动端布局或 disclosure 外观时容易留下旧覆盖。

**建议：**新导航使用自己的一小段 scoped CSS；迁移完成后删除被替代的 `.rail-*` 规则，合并对应断点。避免在文件末尾继续追加第四层“强制修正”。全局 details 规则本轮不连带清理，留到实际组件迁移。

### P2：页面编排、选中对象与业务写入集中，但不是必须全部推倒

`WorkspacePage.tsx:29–175` 同时处理账号/栏目查询、账号创建删除、栏目创建分配删除、未读标记、URL 清理和聊天 scope；178–277 行再混合目录、创建表单、账号多视图和 SkillInspector。子函数 `SeriesWorkspace` 处理栏目设置、改名、添加选题、提交生产及内容组件（280–400 行）。

这里的问题不是“文件超过某个行数”，而是**导航调整需要穿过业务写入和聊天切换**。例如 142–170 行选择账号/栏目时会同时清理 URL 参数，并更新打开中的聊天账号。这些行为必须集中保留，不能每个按钮各自拼一套 URL。

**建议：**先抽出 AccountNavigator，只负责浏览和发出选择/创建意图；仍由 Workspace 页面统一处理选择与现有 mutations。后续再把 SeriesWorkspace 独立为组件、把 URL 选择/清理提成一个薄而明确的模块。暂不新增全局状态库。

### P2：账号内容概览仍会随栏目数增长

`WorkspacePage.tsx:252–254` 为每个有选题的栏目渲染一个 `SeriesWorkspace overview`；`TopicLibrary.tsx:63–71` 每个概览读取 6 条，完整栏目读取 20 条。每个栏目还有 Skill 池查询（Workspace 291 行、TopicLibrary 45 行使用相同 queryKey，React Query 可以共享缓存）。

这已经比“每个栏目铺 20 条”克制，不能说现在仍全部 20 条。也不能把相同 queryKey 的两个观察者直接算成两次请求。但栏目越多，账号页仍会形成越来越长的多段画廊。

**建议：**这是第二阶段的信息组织题：先明确账号概览是“找栏目”还是“验收最新内容”。若保留栏目画廊，可每栏目给少量预览和查看全部；不要在第一阶段重写内容数据接口。未测加载耗时，本审查不宣称存在性能瓶颈。

## 不应误判为问题的现有设计

- 栏目设置已经按需展示：`settingsOpen` 初值 false（294 行），`hidden={!settingsOpen}`（355 行），Skill 池设置仅展开后挂载（377 行）。截图中打开的设置不能证明设置默认铺满首屏。
- 任务摘要默认收起，仅展示计数，展开后最多 5 条：`CreatorTaskSummary.tsx:18–19、35、41–44`。不要再次做一套重复折叠机制。
- 服务器数据已经用 React Query 管理，按账号/栏目区分 queryKey。轮询通常以 active 状态为条件：`api/hooks.ts:10–38`、`TopicLibrary.tsx:68–72`。本轮没有证据要求换 Zustand、Redux 或统一停止所有轮询。
- 聊天 Provider 在 Layout 层，Run 跳转不应重新创建会话：`App.tsx:39–42`、`AgentChatHost.tsx:25–81`。它还保护未发送草稿、恢复焦点。这些都是要保留的行为。
- AgentPage 已拆出附件、输入控制、transcript、Trace、工具详情和计划组件（`AgentPage.tsx:8–25`）。后续可继续分离传输和会话控制，但无需为了“代码整洁”在本次导航改造中重写聊天。

## 对 Gemini 建议的判断

| 建议 | 判断 |
| --- | --- |
| 账号树加层级 | 方向对，但优先减少同时展开的对象；一根竖线不能替代逐步披露。 |
| 换 ScrollArea 消灭粗滚动条 | 可选。原生 overflow 配细 scrollbar、稳定 gutter 即可先解决；必须保持鼠标、键盘、触屏可滚。 |
| 操作只在 hover 出现 | 不完整。至少 focus-within 可见，触屏有常显更多入口；删除藏进更多菜单可以降低误触。 |
| 换 shadcn Tabs | 外观可取，但当前 view 在 URL 中，需保留可直达、刷新和前进后退；不应只换样式再丢掉导航语义。采用 Tabs 时也需补齐对应键盘语义。 |
| 大灰块换图标空状态 | 可做，但先按状态给对按钮，再考虑虚线、图标、留白。少写功能教学长句。 |
| 全站背景、边框、按钮整体改造 | 暂缓。先让工作区动作明确，再统一被触及组件；不把首页动效搬进生产工作台。 |
