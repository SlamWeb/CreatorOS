# RSI 与聊天交接修复验收 · 2026-10-22

## 结论与边界

本轮修复任务状态的交接、重复提交保护、评分恢复与聊天展示，不推倒重写生产架构，不新增模型工具。选题保存当前稿；每次生产冻结所选 Skill 与当前稿；RSI 以独立任务循环试产和评分。旧任务不能跟随之后的 Skill 编辑改变输入。

正式服务没有被本轮测试重启、提交生产或写入测试数据。所有真实调用使用独立 8892 网页、SQLite、Skill 库与输出根 `tmp/rsi-chat-recovery-live-20261022`。运行中出现一次环境重连，原本的服务进程和临时浏览器标签失联；只重开同一隔离库，没有重开正式服务或擅自恢复正式任务。

## 实际从前端走过的路径

1. 原 SPA 账号对话发送改稿与 RSI 请求，DeepSeek 用 `manage_topics` 修改原 ID，没有新增替代选题；以准确版本启动 RSI。界面只有一次整轮用量，工具可按真实 call ID 展开参数/返回。
2. 第一次准备试产遭遇 Windows 目录 rename 拒绝。此时基础 Judge 已保存、Codex 尚未提交，失败事件与用量保留。局部有界重试修复后，从同一历史会话要求恢复，DeepSeek 查账号任务、读取并 resume 原 RSI；轮数、候选、原选题快照及稳定试产身份未变。
3. 后台实际 Codex 一次生成一张图片。聊天查询能够看到独立试用队列的提交与完成状态，普通 Run 为零，不再将空普通列表误判为没生产。
4. 真实 DeepSeek Judge 又返回了 `Invalid JSON: trailing characters`。先保存原公开响应和用量；自动只修复一次 Judge，第二次格式合格；没有再调用 Codex。此分支不是人为注入错误。
5. 此测试明确只授权 1 轮；真实分数 87.5，但一条关键项为 0，所以状态是 exhausted，不伪称达到标准。评分有独立质量问题：rubric 把“不发布、只跑一轮”等宿主操作限制当成图片可见内容要求。这条不合理标准及分数原样保留，本轮不调整旧 Judge 凑分。实际默认仍为最多 3 轮。
6. 在同一原选题另行明确提交一次普通生产，得到待验收 Run。保存其全部数据库字段及 25 个原目录文件 SHA256，作为后续重做的对照，不是未知故障后的自动重试。
7. 从原网页再请求：直接修改同一选题正文、将共享 Skill 另存一个候选、只用该候选从头重做。DeepSeek 的实际工具参数为 fresh + 原 topic ID + 来源 Run/所见版本 + 准确候选 ID/digest。新任务进入待验收，thread 与旧任务不同。
8. 点击具名链接打开实际内容页，对话面板仍保留；页面可看新图、候选 Skill、下载和人工验收入口。新图包含指定的四句例句。两次同题 Run 虽然都是“第1版”，链接用真实短标识区分。
