01产品定位与两分钟介绍

CreatorOS 是本地运行的多账号内容生产工作台。核心不是“再做一个更强的 Codex”，而是把一次性创作组织成可复用、可管理、可追溯的生产流程。

约两分钟的项目介绍

我做的 CreatorOS 面向持续运营多个账号、多个栏目的创作者。直接使用通用 Agent 能完成一次创作，但栏目定位、创作方法、选题队列、产物版本和验收往往需要使用者自己维护。我把这些重复工作组织成一个本地工作台。

用户可以从参考图文中提炼可复用的 Skill，在草稿区查看、修改和试用，满意后入库；内容方法和呈现方法可以组合为栏目，也支持将多份 Skill 融合成新的草稿。再将栏目分配给账号，安排选题并提交生产。

架构上，Web 和运营 Agent 进入共用业务服务。Python Agent Loop 负责业务工具循环与上下文管理，账号会话绑定固定作用域；生产则通过 Codex Python SDK 控制本地执行器，传入本次选题、冻结 Skill 和工作目录。模型决定下一步行动，业务代码检查归属、版本和状态。

工程重点是长期任务的可观察与恢复：用 Run、Revision、Attempt 区分任务、内容版本和执行尝试，保存输入快照、会话回执和逐页产物检查点，校验真实文件后才交给用户验收。Trace 和隔离评测帮助区分模型、工具、交付和测试自身的错误。当前发布仍由用户完成，系统记录链接与指标，没有宣称自主增长闭环。

为什么用户不直接使用 Codex？

不是因为 Codex 无法做这些动作，而是CreatorOS 预先组织了业务对象、操作规则和可视化工作流。你的差异在创作方法沉淀、账号/栏目长期状态、选题与版本管理、受校验交付，不在“模型只有我才能调用”。

这是不是 Codex 套壳？

底层生产智能确实主要由 Codex 提供，应直接承认。宿主提供的是业务事实、授权、工作流和产物生命周期，不把模型能力说成自己的算法。是否有用户价值需要真实使用验证，不能只靠“不是套壳”的标签。

为什么选择自己写 Runtime，而不直接使用成熟框架？

原始动机包括学习和掌握 Agent 工具循环；当前工具规模下，小 Runtime 便于直接控制上下文投影、宿主约束和 Trace。成熟框架也能承载这些职责，不能声称框架缺少这些机制。关键是业务边界是否清楚，不是自研代码量。

你个人的贡献怎么讲？

讲你做过的需求判断、方案取舍、代码审查、失败复现和验收；能展开一段关键源码及其变化。可以如实说 AI 辅助实现，不把 AI 提供的代码或 SDK 内部机制冒充完全独立手写。

Workflow 与 Agent 的边界在哪里？

模型根据实际上下文决定查询、选题管理、是否提交授权的任务及后续工具；输入校验、状态迁移、冻结、验收和审批是固定代码。不是所有步骤都交给模型，也不是每条指令都固定走同一条计划。

账号 Agent 是每个账号启动一个常驻进程吗？

不是。同一 Runtime 加持久化会话绑定、账号目录和工具权限。一个账号可以有多个会话；业务身份长期存在，不要求一条无限延长的 Session。

意图识别是不是单独的分类器？

主聊天路径由运营模型在工具循环中理解意图和选择行动；没有必要把它包装成独立训练的分类器。另有自然语言计划/Preview 路径，不能与主 Agent Loop 混成一个组件。

03Runtime：模型不能直接执行 Python

原始问题：只有一次模型请求，无法完成“先查账号 → 找栏目 → 再查选题 → 决定下一步”的多步任务。

最小解法：维护 Session，用循环反复构建模型输入。模型返回结构化工具请求，宿主按注册表执行，追加对应结果，再让模型判断继续调用还是结束。

load Session + checkpoint
append user request
while guard allows:
    context = build_model_context(ledger, tools, checkpoint)
    response = provider.stream(context)
    if not response.tool_calls:
        return final response
    for call in response.tool_calls:
        result = execute_tool_call(call, runtime_context)
        append matched tool result to ledger

这是解释性伪代码，不是可直接运行的模块。真实实现还有预算保护、取消、Trace、上下文刷新和快照持久化。当前运营循环中的多工具执行按次序处理，不声称并行工具调度。

组件具体做什么
ModelProvider把模型的完整/流式输出转换成宿主统一类型；当前具体 Provider 是 DeepSeek
Tool Registry名称映射到执行函数、描述和参数模型

Provider 和 Runtime 为什么分开？

Provider 处理供应商协议及流式分片；Runtime 处理历史、工具循环和宿主规则。换 Provider 不应要求重写业务工具。当前只是定义了接口与 DeepSeek 实现，不等于所有模型已经测试可替换。

流式工具参数还没接收完就执行吗？

不能。流式事件用于展示和收集；需要完整工具名称和 JSON 参数后才解析执行。将参数分片直接作为完整请求执行，会产生错误动作。

模型连续调用几十次工具怎么办？

每次主请求都重新检查上下文预算，必要时压缩和外置；循环 Guard 限制持续执行。一次用户 query 不等于一次 LLM call，Trace 也按单次请求记录。

04工具有哪些，怎样校验？

工具 Schema 是从注册表导出，不是模型随意写一个 Python 函数就能运行。部分工具参数模型采用严格 Pydantic 校验；类型正确不等于对象归属正确，业务 API 还要检查。

总览和账号模式使用固定 allowlist。账号模式支持栏目组合、绑定更新和共享 Skill 文本编辑，但不开放全局安装/提炼及账号重新分配。融合有 Web/服务入口，当前聊天清单没有单独的 merge Tool；不能说所有 GUI 动作都已经一一映射成 Agent 工具。

一次工具调用要经过哪些门槛？

注册表查找 → 是否对模型暴露/在 allowed_tools 内 → 绑定或拒绝账号参数 → JSON/Pydantic 校验 → 执行服务端归属、状态、版本检查 → 返回结果。错误结果也回填，让模型据此说明或调整。

动态能力注入是否意味着动态生成工具？

不是。当前动态的是账号/栏目/Skill 元数据；工具 Schema 由固定、按模式选择的集合提供。暂不需要 embedding Tool Router 或 deferred tool search。

Skill、Tool、MCP 三者怎么区分？

Tool 是宿主可执行接口；Skill 是方法指令与配套资源；MCP 是工具/资源互操作协议。注册了 Tool 不等于部署了 MCP Server。本项目到 Codex 的当前链路是 SDK/app-server，而不是 MCP。

05账号隔离：Prompt 是引导，Guard 才是约束

例子：账号 A 的会话要求读取或生产账号 B 的栏目。模型可能选错 ID，即使 System Prompt 写了“只能操作 A”，也不能以此为唯一保证。

  1. 会话创建时持久化绑定 creator_id；换账号换会话，不把旧历史重新标记为新账号。
  2. 模型 Schema 和工具参数绑定限制可选范围。
  3. StudioClient 携带宿主会话标识；API Guard 根据真实会话与数据库资源关系检查 Series、Topic、Run、批次等归属。
  4. 新任务写入还要验证版本、状态和 Skill 可用性；旧任务继续依据冻结输入。
20 秒答法

提示词让模型倾向做对，代码阻止错误操作真正落地。我不相信模型传来的账号 ID，而从宿主持久化会话取得作用域，再核对资源归属。

这是开源本机自用的防误操作边界，不是公网身份认证或多租户安全。总览/普通本地 UI 有更宽权限；拥有本机文件/API 权限的人不在这个隔离保证内。Skill 库是共享资源，编辑要说明共享影响。
上下文隔离和操作隔离分别是什么？

上下文隔离限制默认注入的业务资料；操作隔离限制工具实际可访问的对象。只做前者仍可能误写，只做后者则可能在回答中泄露或混淆对象。两层都需要。

Pydantic 为什么不能代替权限校验？

它能检查 ID 是字符串、字段齐全，但无法仅靠类型知道该栏目属于哪个账号。归属必须由数据库关系与宿主身份确定。

06上下文工程：账本完整，请求按需投影

痛点：既不能把长历史全部送给模型，也不能因为窗口压力删掉唯一证据；当前账号状态还可能被用户的新要求覆盖。

组成实际内容处理方式
稳定部分系统指令、运行规则、该模式 Tool Schemas尽量保持稳定，缓存收益需看实际 usage
账号能力树账号 → 栏目 → 当前绑定 Skill 的 name/description每轮重新投影；成功业务写后刷新，不写回历史摘要
旧历史已完成的旧 Turn/Step旧摘要 + 本次新增历史 → 新滚动摘要
近期历史近期完整轮/完整步骤与当前请求优先保留原文，工具调用与结果成组
工具结果原始结果与发送给模型的 DTO 视图按工具类型选字段；硬预算压力时归档 + 引用 + 按需回读

当前 Studio DTO 投影保留 ID、分页、状态、来源和 CAS 所需字段。原始账本不被改写；格式投影失败不应把已经成功的写操作变成失败。不要误称所有近期结果都按固定 16k 字符截断——旧辅助函数存在，不等于当前生产路径调用它。

为什么不是永远按用户 Turn 压缩？

一个用户 Turn 内可能循环很多次。当前优先保留完整 Turn；最新 Turn 本身超保留预算时，沿完整 Step 边界切分，并单独 pin 当前用户要求。Step 包含 assistant 输出及其配对工具结果，不从 tool_call → result 中间截断。pin 是请求投影，不新增一条账本消息。

Summary 和 Memory 是一回事吗？

滚动摘要是当前 Session 的上下文压缩机制；业务数据持久化可以按工具查询，但不等于自动跨会话偏好记忆。当前主线没有完整向量/长期记忆自动提取召回系统。

最近用户要求会不会被长工具循环挤掉？

超长当前 Turn 采用完整 Step 后缀，并 pin 当前用户原文，计入预算。下一用户 Turn 进入后按新边界处理。摘要仍可能丢语义，因此需要约束保留、证据回读与任务评测，不承诺绝不遗忘。

压缩后仍超过预算怎么办？

重新测预算并有限外置大工具结果；外置全文留会话归档，模型得到描述和引用。稳定前缀或用户输入本身仍太大时应明确拒绝/要求拆分，不无限压缩或冒险发超限请求。

Token Budget 与缓存怎么测？

发送前用估算做保护，usage 回来后记录实际 prompt/output/cache。估算不是实际账单；cached 是 input 子集，不能再加一次。SDK thread 累计量也不是单次上下文长度。

20 秒答法

为什么不能只保存消息历史？

消息里说“已经生成”可能与文件或数据库不一致。用户改稿、批准摘要、任务 owner、文件是否解码成功等都需要结构化状态与校验。

为什么保存 thread 还需要自己的 checkpoint？

thread 保存 Codex 会话历史，不知道 CreatorOS 是否成功收取并验收文件。宿主还要知道输入未变、哪些工件可复用、成功 turn 是否有证据，以及当前版本是否允许写入。

08与 Codex 通信：控制消息 + 事件 + 文件

项目使用 Python AsyncCodex。本机安装的 SDK 控制本地 codex app-server 子进程，stdio 上交换逐行 JSON-RPC 请求、响应和通知；不是控制聊天窗口，也不是 CreatorOS 直接请求生图 API。具体 SDK 版本是本次审阅环境的实现事实，不保证后续版本完全相同。

CreatorOS 工具 → 本地 HTTP 业务 API
后台 Producer → AsyncCodex
SDK → codex app-server --listen stdio://
thread_start / thread_resume → 创建或续接会话
thread.turn(TextInput + SkillInput) → 开始一轮任务
事件流 + delivery.json / 图片 → 宿主校验

这是流程示意，不是可直接执行代码。模型/推理强度、cwd、sandbox 等由代码配置。TextInput 传明确任务；SkillInput 指向本次冻结的本地 Skill。看图讨论会实际传 LocalImageInput，不能仅在文字里说“参考某图片”。

协议角色保存与用途
TASKworker_task.json：任务类型、业务 scope、输入引用、交付要求
EVENT消费一次 SDK stream，记录 thread/turn、公开活动及终态；心跳不当内容进展
REPORTworker_receipt.json 留执行证据；delivery.json 留产物索引，调研返回 ResearchReceipt。原业务存储才是任务状态真相

官方协议中 thread 是会话，turn 是一次请求及其工作，item 是消息/工具等事件单位。SDK 能 resume/fork，不等于恢复某条工具执行的机器栈。

thread_resume 到底恢复什么？

恢复会话上下文，随后发起新 turn；不保证原工具从某一条指令继续。新选题、新 Revision 用新 thread；同任务技术恢复在核验输入后才续接。

运营 Agent 与生产 Codex 会共享历史吗？

不会自动共享。运营 Agent 收到业务任务摘要，生产收到冻结任务输入。讨论可 fork 生产历史到独立会话并续聊；fork 继承可见历史，不能说完全清空了上下文。

SDK sandbox 能关闭所有工具吗？

不能把只读文件系统权限理解为禁止所有远端工具。本项目讨论使用减少工具面加事件检测，属于约束与检测，不能撤销已被远端接受的副作用。

调用 SDK 和调用 MCP Server 有什么不同？

当前 SDK 直接操作有状态的 Codex app-server 会话/turn/events；本项目这条路径没有经 MCP。都可能使用结构化协议，不代表协议语义相同。

09可恢复生产：先确认发生了什么

对象含义例子
Run一个业务生产任务一个已入队选题的生产
Revision一版内容要求与产物用户说换切入点，进入新版
Attempt同版的一次执行尝试技术中断后显式恢复，保留旧失败尝试

本地执行器取得数据库对应 OS 文件锁，持久化执行 journal；数据库保存 owner/lease，迟到或失去所有权的执行者不能覆盖新状态。提交检查所见版本，默认幂等创建绑定同选题；这不是分布式调度器。

  1. 执行前准备并冻结输入/Skill，写明真实工作目录。
  2. thread 创建与 turn 开始立即留回执；SDK 事件与工件持续记录。
  3. 校验 delivery 索引、连续页序、路径范围、解码、重复图片与 Hash。生产中的有效工作稿可以更新，旧预览按摘要保留。
  4. SDK 正常结束、完整交付且文件有效后冻结最终检查点，进入 awaiting_approval。
  5. 用户批准的是明确版本与摘要，不允许之后静默改变。

失败后怎样恢复？

情况处理
SDK 已完成，宿主后处理/验收失败先核对持久化 completed 证据与文件，可离线重验交付，不再次调用模型
SDK 真失败/中断，输入仍一致保留文件；用户显式恢复，同版新 Attempt，校验后 resume
交付索引缺失或损坏最多一次无生图的索引修复；不能无限自动重画
输入/Skill/图片被篡改拒绝不可信恢复，不凭同名文件当相同产物
取消/超时或旧进程未确认退出落真实状态，保留证据，阻止迟到结果复活或盲目重启
幂等能保证恰好一次生图吗？

不能。宿主幂等防重复业务写和重复提交，不控制供应商已经接受但本地尚未记录的请求。未知结果先查证、复用已核验文件，仍不宣称外部工具 exactly-once。

事务回滚能把已经生成的图或付费调用撤销吗？

不能。SQLite 回滚只作用于数据库事务，文件和远端工具不是同一事务。项目依靠冻结输入、回执、校验、显式恢复和保留旧版本处理部分成功。

Checkpoint 一张一张保存，就必须一页一个 thread 吗？

不需要。逐页是宿主保存/核验工件的粒度，不要求逐页独立模型会话。当前 native-v1 在同一生产 thread 协作内容与呈现。

有没有并发？为什么不是六十路？

生产是后台执行，页面不阻塞；但当前 ManagedRunExecutor 只有一个生产 worker，忙时拒绝第二项。它解决重复并发提交与所有权，不是多路并发生图。多个 SDK 会话可作为后续方案，不把可实现当已验证。

参考图存了 assets，模型就一定用它生图吗？

不一定。资产存在、模型读取、具体图像请求实际传参考，是不同证据。宿主保留资源和生产器报告的引用，不能仅凭 Prompt 的一句话宣称图像服务使用了某参数。

Skill 安装会污染日常 Codex 吗？

CreatorOS 将 Skill 放自己的库，不安装到全局 Codex skills。生产显式传本次路径/快照。但这不等于完全屏蔽 Codex 本机已有的全局 Skills。

11Skill 融合 ≠ 栏目组合

方式实际行为来源会改变吗？
栏目组合绑定两份 Skill；生产前在同一 thread 检查协作，随后执行不会；本次执行冻结来源
Skill 融合选 2–8 份已登记 Skill，生成一份新的可编辑草稿不会；保留权威来源快照与命名空间资源

融合前扫描受管理文件，限制总文件/字节量，拒绝链接/路径逃逸及不支持类型，冻结来源摘要。给 Codex 可写副本，权威来源快照放工作目录外。新草稿保留安全资源到 assets/fusion-sources 的各来源命名空间；嵌套 SKILL.md 改作 SOURCE-SKILL.md，避免被当第二个可执行 Skill。

融合 Prompt 要求读各来源方法与配套资源，产出一份新 Skill，将硬冲突留给用户决定。它不是简单文本拼接，也没有形式化算法保证任意组合语义兼容。真实样本证明生成可读草稿，不代表所有融合已经试产稳定。

分页/分格由 Mind 还是 Visualize 决定？

Mind 管事实、范围与教学关系；呈现管 IP/风格。内容单元不等于图片数，分页分格综合当前明确要求、栏目约定和两份规则。默认偏好可以适配，未被用户覆盖的互斥硬要求要停下来澄清，不能为六格删成六个词。

融合为什么要保存完整来源资源，而不是只复制 SKILL.md？

规则可能引用脚本、模板、参考图或 references；只拼正文会丢相对路径和生产资料。命名空间避免同名资源互相覆盖，摘要帮助确认实际融合的版本。

用户改了原 Skill，旧融合草稿会自动变化吗？

不会。融合任务绑定来源快照；新操作使用当时的版本，旧草稿保留可复查证据。不静默改写已试用或入库结果。

12调研选题：候选不是正式队列

Codex 调研接收账号/栏目定位、受众、内容 Skill 和该栏目既有正式选题及未入队候选，提示模型参考这些材料减少明显重复，不保证语义去重。它要执行真实联网研究并返回标题、切入点、理由、来源；宿主验证回执和实际搜索证据，才把批次置为 ready。

候选批次先保存在 JSON 工件中。用户选择并确认或明确要求入队后，通过业务服务成为 SQLite Topic；生产只针对有效已入队 Topic。候选来源与切入点进入 brief，后续生产能追溯选题依据。

不同入口的授权不能一概而论：候选选择 UI/prepare_topic_selection 可走 Preview→确认；当前 queue_topics 对明确的入队指令可直接执行，但不生产。查看、建议和调研本身不授权入队，旧 Preview 也不能被无条件确认。
用户要十条，调研只返回八条怎么办？

区分 requested_count 与 returned_count，如实返回不足与原因，不补造、不把实际返回数误称请求数，也不默认重新发付费任务。真实报告中出现过这类缺口。

调研期间栏目或 Skill 改了怎么办？

调研结果有输入快照与指纹；读取、准备选择、确认应按现行契约核对当前配置。发生陈旧状态要按接口提示重新研究/选择，不让旧要求静默写入新栏目，也不能只更新确认版本绕过用户所见结果。

Agent 会自行运营、持续调研吗？

当前仍由用户目标/明确请求发起；查询与建议不自动触发研究、生产或发布。具备工具循环不等于已经实现长期自主运营或定时目标追踪。

默认数据库是 data/creatoros.db；Web 会话在相邻 creatoros-agent-sessions，生产 Skill 库在 data/producer-skills。改数据库位置后相邻目录也变化；outputs 默认仍跟项目，不自动随数据库搬迁。

SQLite 会不会太 toy？

当前是本地、单生产执行者、自用场景，SQLite 简化部署；ORM 与迁移保留演进空间。不能反过来假称实现了高并发分库分表。若多进程/多人共享写入成为真实需求，再处理认证、调度及数据库迁移。

乐观并发和幂等是一回事吗？

版本/digest CAS 判断你看到的对象是否仍是当前版本；幂等判断同一次动作是否已提交。前者防旧状态覆盖，后者防重复副作用；执行锁/owner 又是第三个问题。

JSON 原子写就有事务了吗？

临时文件加原子替换只保护单文件发布，不能保证多个文件、SQLite 和远端请求共同提交。关键回执失败要严格处理，诊断副本可以降级，不能把全部 OSError 都吞掉。

15Eval：不要把跑通、检查通过和质量混算

核心问题：模型说对、工具返回成功、GUI 看起来正常，都不能单独证明任务完成。

  1. 冻结题意、源代码、夹具和判分协议；正式数据做读写守卫。
  2. 从原页面发一次真实用户请求，走原 Runtime/真实 Provider，保留前后数据库及文件快照。
  3. 检查工具对象/参数、实际状态、副作用、最终回复和真实入口；不是只查有没有调用某一个工具。
  4. 语义/图片质量独立阅读，未判定就待复核。模型辅助独立阅读不等于已经接入通用自动 Judge 平台。
  5. 新版本整轮再跑，原失败保留；修采集器或 grader 时明确成绩不可直接横比。
维度具体判据示例
业务目标所需对象、数量和字段正确；只读请求业务记录不变

当前公开指标账本记录已接线 20 个不同场景/21 个执行槽；覆盖规划为 50 个不同场景，仍有未接线部分。接线不是全部通过，重复轮次不是新增题。报告中程序检查、独立阅读、GUI 和质量结论分开统计，不混成无定义的综合分。

工具正确率和任务成功率有什么区别？

工具选得对，最终回复也可能漏条目或编造链接；工具调用数少也不一定差，所需目录已在上下文时可以零调用。任务成功按业务目标与交付判，不强制每题同一工具序列。

怎样做 LLM-as-Judge 才可靠？

未来自动语义评估应固定 rubric、参考证据和版本，对正负例校准，与独立人工阅读检查一致性，不让 Judge 获得策略标签而偏判。当前有模型辅助独立阅读记录，未建立完整自动语义 Judge 接线；不能把评测设计当已实现平台。

怎样证明是 Harness 修复带来的收益？

同题集/协议/模型/预算做可比较运行，开发与验收分开，保留全部首尝试、失败与复核。采集器/grader也改变时必须重建可比分母；不能用前后两个不同定义的总分宣称提升。

Token 成本如何比较？

实际 usage 定义清楚：input+output，cached 是 input 子集；线程累计与本次增量分开；DS、Codex和图像费用不能混为一个已知账单。成功任务子集会有选择偏差，任务失败/重试成本也要说明。

16四个可讲的真实失败，而不是漂亮假数字

A · 查对了，最终回复却交付错了

实际待选标题和任务状态正确，但最终回复漏链接、改错域名或加入无关内容。对照工具原文、模型输入、回复和 GUI 点击，定位为交付问题。宿主从已授权工具 DTO 收集权威入口，前端只激活可信内部链接；原回复与 Trace 保留，原失败不改分。

B · 图已生成，宿主却拒收

生产过程中的内容补稿或音标修图改变了预览。旧 ingest 把中间预览当最终不可变产物，导致有效图被拒收。改为有效工作稿可更新、旧图按 Hash 留证，SDK completed + 完整核验后再冻结；有成功 turn 证据的交付故障可以离线恢复，不重新付费生图。

C · 诊断记录写失败，反过来杀掉正常任务

Windows 文件替换失败从进度观察器冒泡，宿主 interrupt SDK。现在区分权威记录与可选诊断副本；短占用有界重试，持续诊断故障可见降级，真正 SDK failure/关键回执/草稿校验仍严格失败。不扩大权限，不把所有 I/O 错误吞掉。

D · 测试错了，也会让你误判 Agent

将委派给 Codex 的消息强制等同用户原话，或用过短图片等待时间，会产生测试假阴性。按真实工具参数→持久化记录→页面内容关联，并用有界等待确认解码。改判分采集后开新轮，旧失败保留，不包装成模型突然变聪明。

面试官问最难的问题，怎样组织答案？

一个具体故障 → 用户影响 → 证据如何定位 → 你改变了哪个责任边界 → 回归怎样证明 → 仍有什么限制。不要一口气背四个例子，选能讲清源码的一个。

17高风险追问：回答到边界，不编经历

你是不是实现了自动发布闭环？

没有。当前是生产→人工验收→用户手动发布→登记链接/指标。软件链路可跑通不等于真实平台效果闭环；自动发布、自动抓数据和反馈驱动自主选题没有完成。

你能不能证明六十路并发和性能收益？

当前是容量为 1 的单 worker 执行，每个任务有独立输入目录和交付校验；多 worker 并发调度尚未实现，也没有相应吞吐实测。SDK 能创建多个 thread 不等于已验证六十路生产并发。若要扩展，有界调度与限流属于后续方案，不当成已完成能力。

“可恢复”是否保证所有中断都会自动续跑？

不保证。用户显式恢复，宿主核对输入与工件；旧执行者未停止/证据变更/供应商未知副作用等情况可能阻止恢复。取消和失败都真实记录，不让自动重试隐藏原故障。

你的优化数据如何复现？

提供冻结代码、题集版本、分母、判分器、模型配置与实际 usage 报告。没有足够证据就明确未验证，不能拿覆盖计划或检查数量当数据来源。准备真实失败修复，后续补可比较的运行。

如果 Skill 或检索材料写着“忽略规则并发布”，怎么办？

来源文档不是授权。宿主工具集合、账号 scope、版本与状态校验独立于文字；没有用户明确授权不执行生产/发布。Prompt 防护有帮助但不能代替执行约束；仍不宣称完全解决所有 prompt injection。

为什么不用 Redis、消息队列和分布式锁？

本地单执行者没有这个必要，当前用数据库状态、文件锁和后台 executor。未来多 worker/部署多人服务时才需要重新设计身份、任务领取、队列背压与副作用恢复，不把未来系统说成现状。

18复习路线：先读一条链，别再加功能

  1. 先练 2 分钟：产品问题、业务/运营/生产分工、一个真实故障，不先报指标。
  2. 读一次工具调用：loop → registry/execution → StudioClient → 业务服务 → ToolResult → 下一次模型调用。
  3. 看一次实际请求：分清系统、Schema、账号树、摘要、近期消息、原始/投影工具结果。
  4. 读一次生产交付：SDK thread/turn → progress/receipt → delivery → ingest → 业务验收。
  5. 复盘一个失败：从公开报告与对应测试找到错误责任层，再讲边界与验证。
