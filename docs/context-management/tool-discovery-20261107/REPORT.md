# 按需发现工具：隔离原型与真实模型实验（2026-11-07）

## 原型及限制

使用账号 Agent 的完整工具集合及 `ACCOUNT_INSTRUCTIONS`，实验时 Git HEAD 为 `2720cfa16039745c37120047334196136d130a98`；不提供真实账号目录，历史和问题是合成数据。模型是 DeepSeek `deepseek-flash`、非思考模式，通过现有 **Chat Completions** 集成，基线使用完整原工具 Schema。候选只提供两个固定根工具：

1. `discover_tools(names)`：返回所选工具的原始完整 Schema。固定目录通过把每个工具描述机械截取前 75 个字符构造，可能截掉负向规则，只用于实验。
2. `call_discovered_tool(name, arguments)`：要求先发现才可调用；通过账号参数绑定函数和原工具参数解析器校验，在实验中只返回受控合成只读替身，**不执行实际业务处理器**。

Schema 作为 `discover_tools` 结果追加到消息末尾，根工具列表和顺序始终固定；不是 DeepSeek 服务端原生工具搜索，也没有改生产代码。动态工具清单不改变 Chat Completions 根 `tools`，只是把完整 Schema 当成工具结果交给模型；网关的 `arguments` 是通用 JSON 对象，模型不再获得供应商侧的具体函数参数约束，必须由宿主解析验证并拒绝越界。会话内逐渐发现更多工具会使历史里的 Schema 越来越大；原型允许模型重复发现同一工具并再次返回全文，尚无结果去重、过期或安全更新机制。实现生产级网关仍需可靠的用户授权、实际账号资源归属、服务端输入验证、写入幂等与出错处理，本实验不证明这些权限边界。

工具根 Schema 的项目字符规则估算：完整 **15,123 tokens**；精简目录加两个工具 **2,426 tokens**。逐请求实际使用量来自供应商，和 schema 的估算不是同一计量。每个实验变体 system 开头生成不同随机字符串，以降低相互预热；会带来微小 token 差异。变体顺序交错，无重试筛选。模型输出均为原样合成证据，未调用生产、发布、业务处理器或真实数据库。

## 六个独立请求

选题详情、计划状态、Skill 正文、失败任务四个只读场景，基线和原型都选到了预期工具、参数通过宿主解析并在回答中提到替身提供的主要内容；工具路径不应视为唯一可行解。问候场景两边都直接回复，没有工具调用。含糊改名场景，两边都先查栏目；**只读查询本身是合理路径**，测试替身因为该题预设无工具而拒绝返回目录，所以模型随后表示无法确认并未执行改名。脚本机器检查因该拦截而标记 false/blocked；这不能视为模型错误或业务成功，归 `needs_review`，需补真实模拟目录/多路径评分。六个场景、两个变体各一次；无二次筛选。

各格按所有主模型请求累计 `input/output/cache hit/cache miss`；括号为模型请求数：

| 场景 | 完整工具 Schema | 发现原型 |
|---|---:|---:|
| 选题详情 | 39,782 / 92 / 19,712 / 20,070 (2) | 21,080 / 146 / 13,440 / 7,640 (3) |
| 计划状态 | 39,758 / 72 / 19,712 / 20,046 (2) | 21,594 / 134 / 13,696 / 7,898 (3) |
| Skill 正文 | 39,809 / 100 / 19,712 / 20,097 (2) | 21,205 / 184 / 13,440 / 7,765 (3) |
| 失败任务 | 39,760 / 57 / 19,712 / 20,048 (2) | 19,579 / 142 / 12,672 / 6,907 (3) |

真实首次输入分别约 19,830–19,838 与 6,042–6,049；有工具的四个只读例子原型每例额外增加一次主请求。首请求 hit 均为 0；每组匿名结果均使用不同 system 前缀防止相互预热，不能代表真实产品会话的命中率。完整累计包含受拦截用例，不能作为生产降费率：完整工具 **218,672/427 input/output**，原型 **108,866/782**。各组文本及输出长度、服务端缓存状态、模型随机性均不同。

人工核对：两种方案在选题例对“返回数据未显示的附加要求”说法偏绝对，缺少明确完整性证据；Skill 例均说正文只有一句，而替身没有分页字段，不能以此证明生产中一定读取了完整 Skill。其余四个只读例的给定主要字段有替身依据；关键词命中不证明完整语义质量。问候及含糊改名回答全文见 [单轮原始记录](single-turn-raw.json)。

## 三个连续用户轮

固定一个临时会话，依次查询选题、追问该选题的受众、查询另一个计划；每轮间等待 5 秒供缓存持久化，不计入逐模型请求耗时。基线与原型各运行一次，用户问题与受控工具回执相同。第一轮选择和参数均正确；第二轮两边均复用历史，没有工具调用；第三轮都选对并调用计划工具，原型重新发现计划工具。计划工具的完整 Schema 被追加，根 `tools` 未变，且所有相邻请求在客户端对比中均保持消息追加与相同根工具。服务端 hit 是实际值，不能仅凭客户端前缀证明命中原因。

| 用户轮 | 基线 input/output/hit/miss（请求） | 原型 input/output/hit/miss（请求） |
|---|---:|---:|
| 选题 | 39,790/73/19,712/20,078 (2) | 21,086/172/13,440/7,646 (3) |
| 追问 | 19,972/82/19,712/260 (1) | 7,639/81/7,424/215 (1) |
| 新计划 | 40,232/72/39,808/424 (2) | 26,670/144/24,576/2,094 (3) |
| 合计 | **99,994/227/79,232/20,762 (5)** | **55,395/397/45,440/9,955 (7)** |

**结果质量不能按选对工具或关键词判通过。** 原型第一轮输出“选题当前状态为待选”，而替身仅给 `id/title/brief`，并未提供任何状态；这是无依据的状态断言。基线该轮未加入这个状态。第二轮原型把“早上时间紧、常没时间好好吃早饭”说成适合人群，但替身只说“上班族”，这属于推断，未明确标注；基线明确将细分人群描述为推断。原型第三轮“后台仍在推进、没有失败”也超出替身仅有 `status=running` 与消息“进行中”的直接证据。两变体每种仅一次，无法证明这些问题由工具发现造成，但应在接入生产前纳入语义与证据评分；不能说本实验任务效果全部通过。完整记录见 [多轮原始结果](multiturn-raw.json)。

## 下一步和复现

该实验说明在**合成小样本**中，固定目录+按需返回完整 Schema 的方案有明显降低首请求与累计输入的潜力，即使多一轮调用也如此；并且客户端结构与这次实际供应商 hit 支持它在多轮中可维持可复用前缀。但目录截断丢规则、泛型参数约束、语义幻觉和真实业务授权均没有解决；范围、成本与质量不能推广到生产平均。应优先改良目录与宿主安全设计，使用已有专项题集跑真实业务等价的隔离前后对照、错误/跨账号/多意图/失败恢复和更长对话；在此之前不建议把原型替换进正式工具路径。

不加 `--live` 无付费模型调用；指定新路径保留失败，不覆盖历史：

```powershell
D:/Anaconda4.7g/envs/deepcode/python.exe -m tests.live_tool_discovery_experiment --live --schema-snapshot docs/context-management/tool-schema-audit-20261107/all-schemas.json --report tmp/<新目录>/single.json
D:/Anaconda4.7g/envs/deepcode/python.exe -m tests.live_tool_discovery_multiturn --live --schema-snapshot docs/context-management/tool-schema-audit-20261107/all-schemas.json --report tmp/<新目录>/multi.json
```

两脚本在原始运行后增加了可选的 `--schema-snapshot`：以上命令使用当时的 2720cfa Schema；省略时使用当前工作树生成的 Schema。宿主参数解析器仍使用当前代码，模型和服务端缓存状态也可能改变，复跑不等于完整冻结历史环境。

## 补充：缺失信息、多工具及权限自然任务

在前述测试后，账号工具 Schema 已应用机械注解精简；本组**另开一次、各变体只运行一次，不替换之前结果**。完整 Schema 估算是 **14,622**，而不是前组的 15,123；目录方案仍为 2,426。Git HEAD 为 `2720cfa16039745c37120047334196136d130a98`，运行时 `host_contract.py` 有未提交变更；实际发送完整 Schema 的规范化 SHA-256 为 `65f5735afb9856b61f0539993d58486c6603c4dd763225a4533ea49ae3f4dda0`，两种发送 Schema 原样保存于 [robustness-schemas.json](robustness-schemas.json)，不能用 Git SHA 单独重建。完整合成问题、工具参数、实际收到的模拟回执、模型回复及每请求 usage 见 [原始记录](robustness-raw.json)。与上一组因 Schema 及场景不同，不合并估算收益。

四个自然场景对两变体各一次，分别注入只含指定字段的合成只读回执；全部任务、工具回执和账号均为合成。模拟数据刻意缺少部分字段，是缺失信息的故障注入，**不能声称真实业务 get 接口通常会省略这些字段**。不调用任何真实业务处理器，所有未模拟的操作（包括所有写操作）被阻断。以下人工逐条核验，不以工具名或关键词通过代替语义评估：

| 场景 | 完整 Schema | 发现原型 | 证据与结论 |
|---|---|---|---|
| 问选题状态；回执仅有 id/title/brief，无状态 | 回答“待选（pending），尚未入队，也没有生产任务” | 回答“待选……尚未入队……没有任何产物” | **两边均无依据地编造状态及后续状态**；相同故障也发生在基线，不能归因于发现机制。 |
| 问受众具体城市；回执只写“给上班族的早餐故事” | 说“没有限定城市”，并说明未提及具体城市 | 说“没有指定任何城市，明确不了” | 两边都没有编造具体城市；但只能确认回执未提供城市，不能单凭字段缺失断言完整资料绝无限定。 |
| 同时查询选题制作要求和计划状态 | 两个并行只读调用，正确回述已返回的要求和 running | 一次发现两个工具并并行只读调用，但称选题“已入队” | 回执有计划 `status=running`，选题回执**没有入队状态**；原型编造该状态，不应按选对两个工具判通过。 |
| 咨询是否能编辑 Skill，明确不要修改 | 读取 Skill 列表，称其“内置”且可另存本账号候选 | 读取 Skill 正文，称其“共享的已发布版本”且可另存候选 | 两个回执都仅提供 `editable=false/can_edit=false`；**内置/共享发布版的身份和可派生候选的权限均未提供**。两边都未执行写操作，但权限回答不被证据支持。 |

各格为 input/output/cache hit/cache miss（请求数），全部为供应商实际 usage；每个变体 system 使用不同随机隔离标识且首次 hit 均为 0，同轮请求之间并未控制缓存持久化时间。没有真实账单，且输出及模型选择具有随机性：

| 场景 | 完整 Schema | 发现原型 |
|---|---:|---:|
| 缺失状态 | 38,518/90/19,072/19,446 (2) | 20,895/160/13,312/7,583 (3) |
| 缺失城市 | 38,518/92/19,072/19,446 (2) | 20,912/149/13,312/7,600 (3) |
| 多工具 | 38,627/144/19,200/19,427 (2) | 24,151/252/14,976/9,175 (3) |
| 编辑权限 | 38,531/120/19,072/19,459 (2) | 20,740/188/13,184/7,556 (3) |

样本每种路径仅运行一次，故不能由差异推断发现方案必然提高或降低幻觉；但是两个方案都没能在该次缺失状态和权限信息下可靠回答。**在证据不足时正确表示未知，以及真实权限/派生能力校验，必须先有专门测试和可信业务回执，才能评估是否可将工具发现接入生产。**
