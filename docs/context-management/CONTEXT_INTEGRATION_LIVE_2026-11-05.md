# 账号上下文隔离真实模型验收（2026-11-05）

`python -m tests.live_context_integration` 默认不调用远端；显式加 `--live` 才发送真实 DeepSeek 请求。测试在系统临时目录创建独立 SQLite、账号、栏目和会话，启动动态端口 loopback 服务；工具派发额外限定 `manage_topics` 的 list/get，只读执行现有业务路径，禁止其他工具或动作。不会运行历史任务、生产或发布，不记录业务正文或密钥。以下两次测试均用合成数据。

| 执行 | 轮次 / 主请求 | 输入 / 输出 | cache hit / miss | 逐次 hit / input |
| --- | --- | --- | --- | --- |
| 首次，较宽松的列表断言 | 2 / 4 | 26,132 / 249 | 18,304 / 7,828 | 0 / 6,024；6,016 / 6,550；5,632 / 6,644；6,656 / 6,914 |
| 加强列表断言后 | 2 / 4 | 26,179 / 326 | 24,192 / 1,987 | 5,888 / 6,024；6,016 / 6,564；5,632 / 6,661；6,656 / 6,930 |

第二次模型真实调用列表及详情各一次；列表回复验证了两条合成标题，详情回复正确找回未出现在问题中的随机标记。两次同轮工具后请求的 `prefix_comparison.messages_relation` 均为 `appended`；这仅是 Provider 转换前客户端结构对比。独立执行的跨账号只读工具探针被拒，账户业务记录前后相同，Run 数为零、生产调用次数为零。首次已验证随机标记和工具操作，但未检查列表回答内容；第二次补齐了两条标题断言，仍不声称完整列表覆盖。

该测试没有模拟完整产品体验，也没有比较优化前后的真实业务任务成功率。第二次首次请求已有缓存命中，可能与第一次测试的共享前缀或服务端其他缓存有关，不能视为独立冷缓存数据。缓存是 best effort；两次调用的数字不代表生产系统平均命中或节省率。前缀优化的受控单案例对照见下文。

## 位置对照

`python -m tests.live_request_context_prefix` 默认不请求模型，显式加 `--live` 才付费调用。用 `deepseek-flash`、low 思考档及独立随机合成前缀，先后比较原尾部布局与本轮锚定布局；每组一次，使用模拟只读工具和相同固定测试标记，等待 5 秒供缓存持久化，无业务工具或正式数据。最终实现的对照中，原布局后续请求 input/hit/miss = **10,768/6,784/3,984**，锚定布局为 **10,724/10,496/228**；两组均正确返回标记，客户端消息前缀分别不完全相同/完全相同。每组只执行一次且随机前缀不同，服务端缓存 best effort，不能视为线上平均收益或严格统计显著性。
