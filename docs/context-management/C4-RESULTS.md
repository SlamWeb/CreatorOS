# Context Eval：第一轮结果与发现

这是一组用于找问题的合成开发案例，不是可直接写进简历的泛化成功率。模型为真实 DeepSeek `deepseek-v4-flash`，调用现有 Runtime、HTTP 工具与隔离 SQLite；没有触发 Codex、生图或发布。

## 实际跑了什么

1. 单题接线检查：早期约束，三组，报告 `tmp/context-eval-20260913-203151/report.json`。
2. v1：六题×三组×一次，报告 `tmp/context-eval-20260913-203257/report.json`。
3. 审查发现恢复题时间顺序错误：先说禁止创建，历史里却紧接着创建预览。此题v1结果无效，原JSON保留；Markdown汇总会排除此题。
4. v1.1：修正为先授权创建、收到真实隔离库预览，再要求不重复创建。只重测恢复题三组，报告 `tmp/context-eval-20260913-203609/report.json`。不把两版本结果拼成同一次总分。

没有为通过而更改 Runtime、工具说明或模型 Prompt，也没有重复尝试挑最好的一次。

## v1 有效的五题

| 案例 | 完整历史 | 仅近期 | 累计摘要＋近期＋回读 |
|---|---|---|---|
| 早期只回答、不建预览 | 通过 | 未完成 | 通过 |
| 用户改口后的候选和标题 | 未完成 | 未完成 | 通过 |
| 同名栏目准确归属 | 通过 | 未完成 | 未完成 |
| 历史资料指定标题 | 通过 | 未完成 | 通过 |
| 长循环不重复已做预览 | 通过 | 未完成 | 通过 |

v1.1恢复题：完整历史和摘要组通过，近期组未能给出原有预览ID；未创建新预览，未改动队列。

“未完成”不等于不安全。例如近期组多数选择澄清而不是编造，但在完整信息原本存在、应该继续完成的题目中，丢失信息后要求用户重新提供仍不算成功。

## 重点 Badcase

### 1. 测试数据也会影响模型行为

完整历史的改口题准确复述了要求，却把全为 `a` 的批次ID视作占位符，要求额外确认，未执行工具。不能把它归因于忘记上下文。

后续用正常形态的固定随机ID建立新案例；不覆盖本轮记录。恢复题的旧顺序错误也说明，审查夹具与审查Agent同样重要。

### 2. 摘要有信息，Agent 仍可能走错工具

同名题摘要保留了账号、栏目、批次和第二条选择；但将“批次第二条”泛化表述为“第二条内容”，后续模型查询正式选题队列，遇到空队列后停止，没有查询调研候选。

这更像工具概念/状态区分错误，摘要措辞可能参与其中；单次不能确定因果。下一步应对比候选批次与正式队列的说明和不同表述案例，而不是直接增加摘要长度。

### 3. 回读与累计进度有实际作用

- 指定标题题：摘要组实际读取 index.json、归档正文，再准备带正确标题且保留来源的预览。不是碰巧从近期输入抄答案。
- 长循环：近期组保留了用户原话，却丢掉“c1已经做完”的进度，重复为c1创建预览；摘要组只补做c2。说明“只保用户query”不足以保存执行状态。

## 成本怎样看

包含摘要以及后续全部模型请求的input/output，不把cache hit重复相加。单次结果的耗时和缓存只用于诊断；仅近期组直接停下省Token，不算优化。

v1中完整历史与摘要组**共同成功的三题**（早期约束、证据、长循环），输入＋输出Token合计分别是72,522和67,988。这不是计费金额，也不能据此宣布稳定节省比例。摘要增加输出开销，回读还会再次占用输入。

v1.1恢复题单独比较则相反：完整历史9,934 tokens，摘要组16,510 tokens。短历史强制两次摘要的开销未被后续一轮摊平；不能只展示节省的题目，生产触发阈值也不应照搬测试的200-token保留预算。

逐请求真实usage、合成原历史、请求视图、checkpoint、Trace、最终operation和失败检查项保存在上述本地报告目录；汇总代码不把缺失usage补成零。

## 边界与下一步

- 每题每组一次；合成重复背景和200-token近期保留预算，不是1M长上下文压力测试。
- 恢复是落盘后重载和新宿主调用，不是强杀进程/断电恢复。
- 安全宿主禁止生产，队列不变不是模型理解约束的充分证据；判分还检查错误尝试、重复预览和应完成字段。
- 本轮不评价自然语言整体质量，没有LLM-as-Judge，不以指定工具顺序计成功。
- 下一步：针对“候选 vs 队列”复现并做一个小修复，再用新形态ID、不同账号名/表达的保留案例验证；继续区分任务正确性、摘要信息保留与工具行为，避免为开发集调参。
