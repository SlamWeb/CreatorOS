01 / THE PRODUCT

先用一句话认领你的项目。

CreatorOS 把账号、栏目、选题和内容生产组织成可检查、可恢复的运营过程：模型理解用户要求，服务落实业务规则，Codex 根据 Skill 生产内容，用户在 Studio 验收具体版本。

今天最完整的演示终点是产物生成 → 检查 → 返工 → 人工批准。实际平台发布、效果反馈驱动选题与完整自治调度仍是后续目标。这并不妨碍项目有工程价值：一篇内容要能关联到正确账号、保留失败尝试、恢复上下文，并且批准的确实是用户看过的那一版。

当前产品主线

自有账号 → 栏目 → Topic → 图片包

例如一个“AI 工程知识”账号，下设“每日一个 Agent 概念”栏目。用户决定选题顺序，栏目关联生产 Skill，Codex 生成图片与文案，CreatorOS 管理产物生命周期。

保留的业务实验线

知乎热点 → 作者匹配 → 分身回答

PersonClone 提供已有博主的画像与生成能力；CreatorOS 获取热点、计算作者候选、解释用户选择，再向指定分身提问。原来的 RAG 与生成系统继续独立存在。

项目价值，落在“模型调用之间”。

通用 Agent 已经能读资料、调用工具和产出图片。CreatorOS 值得继续做的地方，是把一次次调用变成有业务身份、有验收标准、有历史、有反馈的运营任务。例如：“第二个账号的 Redis 栏目，把幂等放到明天；刚才那篇只改封面”——模型需要理解这句话，但 Topic 顺序、版本归属和旧产物保护，应当由代码给出稳定结果。

读法建议：第一次读 01–05，建立产品与业务全貌；第二次读 06–09，理解底层工程；第三次读 10–12，练习面试表达。不要试图一次记住所有类名。
02 / WHY WE GOT HERE

每次转向，都对应一个真实问题。

① 从最小 Loop 开始：学习模型如何真的“行动”

最初问题：会调用聊天 API，不代表理解 Agent。于是从 messages、while 循环、时间工具开始，让模型提出工具调用，Python 执行，再把结果交还模型。

为什么逐步拆类：第二个工具暴露 if/else；带参数工具暴露 Schema 重复；更换 API 暴露 SDK 依赖。Tool、Pydantic、Provider 和 Runtime 的边界，是沿这些问题拆出来的。Pi 是设计参考，CreatorOS 没有 fork Pi。

依据：根 SPEC 的学习切片记录今天的 Agent Loop

② 接 PersonClone：把“能回答的分身”变成可调度的产能

原始想法：发现知乎热点，为合适博主分身分配题目，再生成内容，形成多作者矩阵。已有 PersonClone 擅长作者语料、RAG 和风格生成；CreatorOS 应该处理“今天让谁回答什么”。

选择 HTTP 服务：PersonClone 独立运行。CreatorOS 复用 Cookie 调正式 API，避免复制整个项目、模型和索引环境。作者入库的抓取、索引、聚类属于 PersonClone 的内部流程。

HTTP / SSE 接入画像契约

③ 多领域原型：一个作者不该被压成“平均兴趣”

真实问题：一个作者既写投资，也写婚恋。把所有历史平均成一个向量，可能让两个擅长领域都不突出。PersonClone 聚类历史标题生成多个领域原型，CreatorOS 用热点对这些原型求相似度，再在每位作者内部取最大值。

主动收敛：我们讨论过人格视角双通道与 LLM 重排；后来担心模型凭空编造热点视角、增加抓取和分析时延，所以先落地 domain-only。现在保留接口，不把愿景写成当前算法。

domain-only 路由提交画像向量缓存提交

④ 自有栏目 + Skill：让作品可以走向真实运营

触发转向：你意识到，要把大量真人分身持续公开发布，账号资源、身份表达、授权与真实反馈都难处理。与此同时，“每天一个知识点”“图文解释一个概念”的生产方法可以复用，并不依赖模拟某位真实作者。

因此：Creator 从“一个知乎作者分身”扩展为“一个由用户运营的账号”；Series 表达账号下的栏目；Skill 表达栏目采用的生产方法。Skill 本身不是账号，而是账号的生产配方。原创栏目让选题、生产、验收和未来反馈更容易形成可观察的闭环。

SocialContentPack知识轮播 Skill账号 / 栏目 / 选题存储

⑤ Codex-as-Tool：把内容生产交给已有的强能力

问题：要自己重复搭调研、生图、工具执行环境，成本很大；你已经在使用 Codex。于是用“Topic + 栏目约束 + Skill 输入，图片与文案输出”的边界，把 Codex 作为端到端生产者。

代价与收益：省去重复实现生产 Agent，获得现成能力；同时要处理长耗时、结构化回执、文件归属、取消和 thread 恢复。CreatorOS 的责任越来越明确：运营管理与可靠交付。

Codex Producer可恢复生产服务

⑥ Studio：从“会话里藏着结果”到“用户能管理工作”

问题：CLI 菜单很难同时展示账号、栏目、队列和图片。长任务占着输入，也让你不知道当前进展。

选择：React 展示业务状态，FastAPI 复用服务；HTTP 提交后立即返回，后台继续生产，SSE/轮询让页面观察状态。你可以继续浏览其他栏目，生产结果留在具体 Run 上。S1–S7 逐步打通这些路径。

Studio 总规划S7 交付记录

这里的产品动机来自我们已确认的对话；实现顺序来自 Git 与 SPEC。保留旧业务能力是为了复用既有成果，不代表现在要同时推进两套产品闭环。

共享的是什么？

Web 和业务 CLI 可以复用 Operation、ContentRun 与 Repository。CLI 通用 Loop 和运营 Parser 复用模型适配器。Producer 既能被早期 Tool 调用，也能被 ContentRun 服务调用。

没有自动共享什么？

Web Parser 不加载 CLI 的 sessions/latest.json。Codex 有自己的 thread 上下文。Studio 生产服务不经过通用 Tool Registry。早期 produce_content_pack Tool 也没有自动包上完整的 ContentRun 审批生命周期。

面试中的精确表达：“我们采用混合架构：CLI 保留工具调用型 Agent；Studio 将自然语言解析放在受限决策边界，将业务写入与生产恢复放在确定性服务中；内容创作内部交给 Codex Agent。”当前还不能说所有业务都由一个统一的自治规划器调度。
04 / PERSONCLONE ROUTE

知乎作者线：谁适合回答哪一道题？

  1. 先获取候选，而不是让模型凭空找热点

    知乎官方热榜 API → HotTopic(rank, title, url, summary, thumbnail_url)。summary 可以为空，不能承诺每条都有完整问题介绍。站内搜索是独立工具，能拿问题、回答、文章的文本与来源；当前 route_hotspots 不自动为每个热点再搜索回答。

  2. PersonClone 负责作者资料，CreatorOS 只消费正式画像

    通过作者列表与 GET /api/personas/{author}/routing-profile 读取画像。按两项目约定，PersonClone 对历史回答/文章标题做 BGE-M3 向量化与余弦层次聚类，提供领域原型及代表证据；CreatorOS 不读取它的本地语料和 Qdrant。画像缺失或状态不允许领域匹配时，跳过并记录原因。

  3. 把文本编码成向量，避免逐对调用 LLM

    热点侧使用“标题 + 最多 4,000 字符的问题介绍”；作者侧使用“领域标签 + 描述 + retrieval_text + 代表标题”。本地 BGE-M3 编码为 1,024 维向量。我们用自己的文本投影生成本地路由向量，不通过 vector_ref 直连 PersonClone 的内部存储。

  4. 对每个热点，先算原型相似度，再汇总到作者

    score(作者 a, 热点 h) = max(cosine(h, p))，p 属于作者 a 的领域原型。命中的具体原型一起返回，能解释“为什么推荐给这个作者”。当前 confidence 随结果携带，但没有被乘进 domain 分数；没有加权平均，也没有最终 LLM 重排。

  5. 把同一套分数转成“每位作者的候选队列”

    build_daily_plans 对每位作者按热点分数降序保留 Top-K。热点 → 作者和作者 → 热点，是同一套分数按不同方向查看。允许多个作者命中同一热点，不强制独占，也不保证低相关作者每天都必须生成。

  6. 用户选择后，才调用分身生成

    简单对话由 route-and-answer Skill 指导模型：路由 → 展示候选 → 等待选择 → ask_author。批量的宿主侧流程用 SelectionPlan 展开为多个“作者 + 热点”任务，支持位置、热榜名次、Top-N、全部与排除作者。去重后可以通过原生 AsyncClient + Semaphore 并发请求 PersonClone，各请求独立消费 SSE。

真实送去 embedding 的文本形状

热点标题：年轻人为什么开始买高股息股票？
问题介绍：围绕稳定现金流和风险展开讨论……
领域标签: 投资策略与股息率
领域描述: 讨论股息、估值与风险
检索文本: ……
代表标题: 高股息是否等于低风险, ……

这是说明格式的虚构例子，不是本轮实时热榜数据。

M × N 到底算了几次？

假设 50 个热点、7 位作者合计 100 个原型：

  • 热点编码：50 段文本。
  • 首次原型编码：100 段；缓存命中后可为 0。
  • 相似度：50 × 100 = 5,000 次 1,024 维向量比较。
  • 结果汇总：50 × 7 个作者—热点分数，再取每位作者的 Top-K。

向量比较不等于模型推理。当前代码使用本地循环计算 cosine，并非发出 5,000 次 embedding 或 LLM 请求。

手算一个例子，你就能讲清 Max Similarity。

虚构热点作者甲·投资作者甲·婚恋甲的最终分作者乙·科技
高股息股票.86.19.86.28
亲密关系边界.12.81.81.15
Agent 工具协议.31.17.31.89

作者甲取 Top-2：高股息、亲密关系；作者乙取 Top-1：Agent。甲的“投资”原型不会被“婚恋”原型平均稀释。不过 Max 也有偏差：原型更多、标签过宽的作者更容易偶然命中，未来需要通过人工样本判断是否加入阈值或分数校准。

缓存为什么不会永远旧下去？缓存按原型身份保存，并检查 corpus_version + embedding_model + dimension + embedding_text 的 SHA-256。任意一项变了就重算、覆盖该项。当前每次路由仍会获取画像以核对版本；热点文本每次重新编码。缓存的是原型向量，不是“永远不更新的作者”。

保留结构 perspective_prototypes 已有数据模型和文本投影，但当前主路由过滤为 domain；evergreen 与 experiment 队列当前为空。SelectionPlan 的批量表达能力也不等于所有自然语言说法已经被统一解析和充分评测。

从用户一句话到可见作品，实际发生了什么？

  1. “给每日 Agent 栏目加‘工具协议’和‘上下文压缩’，把工具协议排第一。”

    Studio 把用户要求、当前栏目 scope 和数据库目录交给 OperationPlanParser。DeepSeek 通过结构化输出生成 OperationParseDecision：明确可做就给 plan；缺信息就 clarification；超出能力就 unsupported。当前只支持 add_topics 和 reorder_topics。

  2. 先看 Preview，再确认写入

    Pydantic 检查结构，Executor 检查栏目、Topic ID 与完整顺序。用户看到前后变化，确认时再核对计划版本和队列指纹。确认成功后，在同一数据库事务内写入队列、操作状态与事件。用户的“确认”来自真实按钮/请求，不由模型自己在 JSON 里声称。

  3. 从某个 Topic 显式开始生产

    创建 ContentRun 时冻结账号、栏目受众与描述、题目和 brief 等输入。HTTP 提交后返回已接受的状态，后台执行器负责工作。栏目里的选题顺序是内容队列，但当前没有每天自动取下一条生产的调度器。

  4. CreatorOS 调用 Codex，Codex 内部完成创作

    CodexProducer 读入 knowledge-to-carousel/SKILL.md 和产物契约，加上选题、受众和返工要求，运行本地已登录的 codex exec。新篇用新 thread，同篇技术恢复或返工复用 thread；工作目录对应本次产物 Attempt。

  5. 先拿结构化回执，再形成最终作品目录

    Codex 返回真实生成图片的源路径、卡片顺序、内容摘要、发布文案与来源。CreatorOS 解析 ProductionReceipt，核对图片来源，复制到自己的输出目录，填入可信业务身份，生成 SocialContentPack。图片张数由内容需要决定，契约允许 1 张及以上。

  6. 验收与批准一个明确版本

    服务校验 Manifest、图片可读性、顺序、尺寸与路径，计算 digest。Studio 展示真实图片和文案。用户可以提出返工形成下一版，也可以批准当前版；批准状态表示验收通过，尚不意味着已发布。

Skill 到底负责什么？

knowledge-to-carousel 固定“用一个保真类比解释零基础知识”“大图少字”“整套视觉一致”“按内容需要选择卡片数量”“输出图片与结构化交接信息”。它降低临时编排的不确定性，但不会决定该给哪个账号发、何时发，也不替代最终质量检查。

对象责任为什么分开
Skill告诉生产 Agent 如何完成这一类内容可更换内容方法，不让数据库规则混入写作提示
Producer Tool / Adapter启动 Codex，解析回执，收集产物屏蔽进程、JSONL、文件交接细节
ContentRun 服务身份、尝试、版本、恢复和批准业务事实不能靠一段生成文字维护
MCP（后续）让外部宿主以标准协议调用能力真正出现第二个宿主时，减少重复适配

当前两个“看起来已经有、其实还没接完”的点：

① Series.skill_name 已存储，但 Producer 的提示词读取与产物字段仍固定为 knowledge-to-carousel，还不是任意 Skill 的动态分发器。

② “Codex 为栏目 deep research → 生成 Topic 列表 → 反馈后调整顺序”是我们确认的产品方向，目前还没有独立、打通的选题研究生产工具。策略字段存在，也不代表自动补货、自动发布和定时调度已运行。

06 / THE AGENT LOOP

Runtime 是把模型的决定落到现实中的那层代码。

先从例子理解：用户在 CLI 说“看看今天的热点，给我推荐作者”。模型本身不会访问知乎；它输出一个工具名字和 JSON 参数，Runtime 校验并执行，再把结果放回对话，让模型知道刚刚发生了什么。

用户输入 → 追加 user message → 保存 Session
    ↓
构建 ModelContext → 检查预算 / 必要时压缩
    ↓
Provider 消费流式响应 → 汇总成 ModelResponse
    ↓
没有 tool_calls → 本次任务结束，等待用户
有 tool_calls   → 校验参数 → 执行工具 → 保存 tool message
    └────────────────────────────→ 再请求模型
模块 / 类型它是什么它解决的具体问题
AgentStatemessages、status、turn、tasks把一次运行用到的状态放在一个对象里；turn 是模型调用计数，不是图片版本
RuntimeContext项目根路径、操作系统、Shell工具知道去哪读文件、在哪运行；不是另一份聊天摘要，也不会自动全发给模型
ModelContext一次请求的消息与工具快照完整档案与模型实际看到的内容可以不同，便于投影和压缩
ModelProvidercomplete / stream 的协议Loop 不绑定 SDK 返回对象；当前实际适配器主要是 DeepSeek
Tool + ArgsModel描述、Pydantic 参数模型、执行函数同一参数定义生成 JSON Schema，又做执行前校验，减少两份 description 漂移
ToolResultcontent、is_error、error_type、retryable、details不同工具以统一形式报告成功或失败；模型填写工具参数，结果由代码产生
AgentEvent回合、工具、usage、状态等通知终端显示与执行逻辑分离，避免 UI 控制业务

为什么把 chunk.delta 转成自己的 TextDelta？

SDK 的 chunk 是“厂商怎么传数据”，TextDelta 是“我们收到了一小段文本”。工具参数也可能被拆成很多段；Provider 转成 ToolCallDelta，Runtime 按调用标识累积，完整后形成 ToolCall。on_event 是上层传进来的回调函数：每收到事件，通知 UI 或观察者。

当前 Loop 等模型本轮工具调用收集结束后，再按 for tool_call in response.tool_calls 顺序执行。工具增量可见，不等于已经提前启动工具；PersonClone 的批量异步能力，也不等于整个通用 Loop 都已并行。

SkillLoader 不是第二套执行器。

默认扫描 creatoros/skills/**/SKILL.md，读取 name、description 和 location，把短清单注入 system。模型匹配到任务后，用 read_file 读完整 Skill；正文引用的契约等资源再按需要读。<available_skills> 是帮助模型识别边界的文本标记，不是 API 新角色或权限机制。

Loader 保留内部 load() 方法用于程序读取，但没有必须暴露一个 load_skill Tool。生产用 Codex 时则是另一条路径：Producer 已经知道使用哪个 Skill，因此直接把正文与契约放入生产请求。

当前有哪些模型可调用工具？

共 14 个默认暴露的工具；route_and_answer 另作为内部 Runner 保留。

  • 基础：get_current_time、get_current_date、read_file、read_tool_result、write_file。
  • PersonClone：list_authors、add_author、get_author_job、wait_author_job、ask_author。
  • 发现与路由：get_zhihu_hot_list、search_zhihu、route_hotspots。
  • 内容生产：produce_content_pack。

Registry 是本地 Python 目录；当前没有 MCP Server，也没有默认通用 bash Tool。自然语言栏目操作走独立 OperationPlan 服务，不在这份列表里。

Runtime 的边界在哪里，还不够成熟的是什么？

默认 MaxTurnGuard 为每个用户任务 30 次模型调用；没有 repetition guard、通用自动重规划或所有工具自动重试。read_file 拒绝敏感路径并限制文件大小，write_file 默认拒绝覆盖。强模型可以处理很多错误，但程序仍需保障参数有效、状态不被误写和执行可停止。

当前会话只使用 latest.json；AgentState 的计数和 tasks 不是完整持久化工作流。中途打断工具可能留下未完成的调用链，还需要专门的恢复测试。自定义 Provider 协议也不等于已经验证所有厂商兼容。

07 / CONTEXT ENGINEERING

模型每次看到的是工作副本，完整历史留在档案里。

上下文管理的目的，是让模型在有限输入预算内保留“完成下一步必须知道的东西”。并非所有日志、图片和工具结果都值得每次原样发送。

磁盘上的完整记录
System
用户 turn 1 → 模型工具调用 → 完整工具结果 → 回答
用户 turn 2 → ……
用户 turn 3 → ……
新用户请求

例子中的 turn 指从一条用户输入开始的整组对话；可能包含多次模型调用。

一次请求的真实组成

messages 字段：
  稳定 system / developer 前缀（含 Skill 元数据清单）
  + 累计摘要（有 checkpoint 时，以 user 角色注入）
  + 保留的完整近期回合
  + 新增消息

tools 字段：独立的工具 JSON Schema 列表

Provider 还设置模型、stream、输出相关选项等。

这里“system 和 tools 靠前、保持稳定”有利于复用相同请求前缀，但缓存是否命中、如何计费由模型服务决定。CreatorOS 不实现服务端 KV cache。SDK 的 tools 是独立字段，不能把图里的上下排列误解成真的把所有工具文本拼进第一条 message。

预算如何触发压缩？

  1. 根据 Provider 配置的窗口与预留输出，得到 input_limit = context_window − reserve_output_tokens。
  2. 调用前用本地估算器估计当前输入；达到可用输入窗口约 90% 时 needs_attention 为真，Loop 尝试压缩。
  3. 从末尾向前按完整 user turn 保留，尾部目标约为输入预算的 1/8，并限制在 8k–128k；至少保留最新 user turn，单轮太大时可能超出目标。
  4. 把旧回合交给摘要模型，输出含 Goal、Progress、Decisions、Facts、Next Steps 等标题的 Markdown。
  5. 新 checkpoint 原子写入成功后，重建请求；原始 Session 不删改。没有可摘要旧回合就不调用摘要模型；仍超预算时当前主要发出警告。
代码中的配置例子，不是厂商最新规格声明：当前 DeepSeekProvider 配置窗口 1,000,000、输出预留 32,768，因此可用输入 967,232，近期尾部目标 120,904 tokens。换模型时应核对并配置窗口。API 返回的 usage 是刚完成请求的真实值，不能提前告诉我们新增消息后的 token 数；当前下一次预检仍重新估算，尚无基于历史 usage 的校准器。

Tool Result 的两次截断，目的不同。

主任务请求：保留首尾共 16,000 字符

大结果中间用 marker 替代，标明 result_ref；用于避免主模型重复读大量文本。完整工具 content 仍保留在 Session，可用 read_tool_result 分页找回。

摘要请求：保留首尾共 4,000 字符

摘要任务只需要提取目标、决策和关键事实，使用更紧的旧工具结果投影。这个步骤不会先在磁盘上把完整结果截断。

这两个数字是字符数，既不是 token 数，也不是 KB。省下的是请求体，不是抹掉档案。仅取旧历史的一部分，通常本来就比完整上下文小；截断还有控制摘要成本与抑制冗余的理由，不能一概说“旧历史子集一定会撑爆”。摘要提示、已有摘要与未来超大工具结果仍需预算管理。

第二次压缩会将“上一次累计摘要 + 新被淘汰的回合”重新生成一份累计摘要，不是一直追加多个摘要。当前没有严格的摘要 token 上限、事实保真评测或 split-turn 策略；“保留关键信息”的 Prompt 也不能保证模型绝不遗漏。

09 / DURABLE WORK

“重启后继续”，需要恢复的是业务事实。

想象一篇内容生成到一半网络断了。用户的愿望仍是完成同一篇；如果他改口说“封面重画”，则是改变作品要求。这两件事不能都叫“再跑一次”。

Run · 同一篇业务任务

“给这个 Topic 生产一篇轮播”。稳定身份、幂等键、当前状态和批准结果。

Revision · 一次内容版本

用户改变要求时产生下一版。上一版仍可检查，旧批准不能沿用到新图。

Attempt · 一次执行尝试

网络失败或中断后重试，仍服务同一 Revision；尝试编号增加，保留错误、耗时与 usage。

queued → producing → validating → awaiting_approval → approved
             ↓              ↓              ↓
       interrupted / failed          用户要求返工
             ↓                         ↓
    同 Revision 新 Attempt        新 Revision 新 Attempt
             └──────────────→ 显式执行 / 恢复
真实故障当前机制保证的边界
双击“开始生产”业务幂等键 + 状态检查同一 Topic 不重复创建同一任务；不承诺外部副作用 exactly-once
旧页面批准新状态expected_version + Revision ID + digest批准绑定用户所见版本与图片字节
编辑期间别处改了队列计划 revision/version + 确认指纹陈旧确认被拒绝，需要重看 Preview
旧 worker 晚到返回owner / lease 条件校验失去所有权的执行者不能覆盖当前业务状态
Windows 进程残留OS 锁、执行日志、Job Object 回收未确认停止时阻止恢复；心跳只表示执行器存活，不代表图片正在变好
执行多个数据库动作中途失败同一数据库事务相关业务写入回滚；已经花掉的模型费用和生成文件不能靠 SQL 回滚

revision、version、hash 是三个不同问题：revision 表示用户改了第几稿；version 表示记录是否被别人更新；hash 表示内容或队列快照是否变化。它们服务不同的一致性检查，不能互相替代。

已经发生过的真实 bad case

S7 的一次真实生产里，Codex 已经生成部分图片，但返回“制作中”的部分回执后没有正常完成。我们显式中断，Run 记录为 interrupted；收紧最终回执要求后，复用同一 thread 恢复，最终得到 7 张图片，重开数据库仍是 awaiting_approval。

验收记录中的恢复尝试 usage：input 404,789，cached input 378,752，output 5,037。这是该次尝试所记录的消耗，不是模型窗口大小，也不是普遍性能结论。一次成功案例只能证明这条恢复路径可行，不能据此声称 Recovery Rate 100%。

Web 为什么不会一直卡住？

生产请求先认领任务并持久化，然后交给容量为 1 的后台线程，HTTP 返回 202。页面通过 SSE 观察业务事件，断线时可以重新获取状态并用轮询兜底。换页面不会停止生产；关闭服务则中断本次工作，重启后需要显式恢复。当前忙时返回现有 Run，没有完整的自动任务队列或分布式 worker。

要恢复业务不一定需要重新加载全部对话：任务状态在 SQLite，作品在目录，生产会话以 thread ID 关联。origin_session_id / context_snapshot_ref 为未来 Side Chat 关联留了字段，但当前没有 Side Chat 产品能力。

10 / WHAT MATTERS NEXT

下一步，让 Agent 对真实任务的完成负责。

我的判断：主线继续放在自有知识栏目运营。你不缺“还能接什么”的想法，最需要的是一组可以反复执行、能明确判定成功的任务，来决定该优化哪个模块。S7 验证产品流程能通，下一步应把“用户说得不标准、历史很多、执行失败”变成可重复的问题集。

01

先建立小型 Agent Eval，定义“做成了”

从当前支持的运营动作出发，收集 15–20 条真实表达：同义改写、跨栏目歧义、先添加再调序、用户中途改要求、越界请求、旧 Preview 确认。固定初始 SQLite 与用户输入，用真实 DeepSeek 解析；执行后比较最终数据库与期望约束，允许合法但不同的计划路径。

衡量：主要报 Task Success，以及成功任务的 token/时延；失败按“理解错、引用错、执行错、恢复错”归因。当前 Parser 是受限的一次结构化决策，应称为受限运营任务评测；不能因为有一个 LLM 调用就包装成完整通用 Agent Benchmark。

02

把真正有价值的自由度交给 Agent

先打通“为指定栏目调研一组选题 → 返回列表 → 用户选择/授权 → 进入现有生产”。把 Codex Research 放在单独输入输出契约内；CreatorOS 根据账号定位、已做内容与用户要求选择。保持现有操作确认和 ContentRun 作为可靠执行边界。

优化理由：现在自然语言只支持新增/调序，缺少连接研究、选择与生产的运营决策层。这个缺口比先接大量外部工具更影响产品闭环。通用多 Skill 分发也应由第二个真实栏目生产需求推动。

03

用反馈做最小记忆，证明它改善下一次决定

先把人工返工和验收理由做成结构化反馈，再构造少量栏目经验，按需注入下一次 brief。做成对任务：有历史时能否避免重复选题、遵循已经确认的风格要求；无关栏目的偏好是否被隔离。

衡量：与不提供历史的基线相比，任务成功、重复选题和返工原因如何变化。先有证据，再决定需不需要语义向量库或外部记忆框架。

04

把恢复和成本变成可回归的工程指标

使用故障注入覆盖网络中断、旧 worker 回写、文件被替换、用户返工与重启。便宜的隔离生产器用于反复验证状态；少量真实 Codex 运行用于验证外部协议和产物。两类结果分开报告。

优化理由：“能生成一次”容易展示，“失败后不重复开工、不批准错图、记录花了多少钱”更能证明你的系统设计能力。

每个模块都应有一个可以回答的优化问题。

模块值得测的问题由证据决定的改动
意图与计划用户说“第二个”“刚才那个”，能否准确消歧？显示快照、引用机制、澄清策略
Context压缩后是否仍记得作者 ID、约束、待办？摘要评测、预算校准、必要字段保护
Memory反馈被保存后是否影响下一次正确决策？作用域、召回时机、经验有效期
Producer长任务是否返回完整契约，何种失败能续接？回执校验、超时分类、thread 生命周期
Routing最大相似度是否被宽泛或过多原型误导？阈值、校准、必要时重排
运行服务恢复后会不会重复执行或污染已批准内容？幂等、owner、版本与文件一致性
你的主张可以是：“模型负责有歧义、需要判断的部分；业务服务负责身份、状态和副作用。通过任务评测决定哪些判断值得自动化，再用可追溯反馈改善下一次决定。”这比“我用了很多 Agent 技术”更能被面试官追问，也更能被你验证。

当前暂缓：大而全的记忆平台、分布式多 Agent、强行补回人格向量双通道、仅为简历而建 MCP、公网自动发布。MCP 在需要第二个宿主复用研究/生产服务时有明确价值，届时再实现标准协议边界。

11 / SAY IT WITH REASONS

面试时，先讲一个任务，再讲一个取舍。

90 秒项目介绍

“CreatorOS 是面向自有内容账号的运营 Agent 项目。我最早从 Python Agent Loop 学起，接过知乎热点和 PersonClone 作者路由；后来把主线调整为知识栏目的图片生产，让选题、验收与反馈更容易在真实运营中验证。

现在用模型把自然语言要求转成结构化运营计划，用户看过 Preview 后由服务执行；内容生产通过 Codex-as-Tool，输入选题、栏目约束和 Skill，输出图片包。长任务用 Run、Revision、Attempt 区分业务任务、改稿和技术重试，持久化 thread 与事件，支持中断恢复和精确版本批准。

底层保留 Provider、Tool Registry、流式事件、Session 和上下文压缩。接下来重点用真实运营任务评测意图和执行，并把用户反馈做成能影响后续选题的运营记忆。”

按当前源码表述；Agent Eval 和反馈记忆这里用“接下来”，获得实际结果后再改成完成式。不要背完一串类名，挑自己最熟的恢复案例展开。

1. 为什么不直接把任务交给 Codex？你多做了什么？

一次性内容生产确实可以直接交给 Codex。CreatorOS 管理的是跨次调用的运营事实：作品属于哪个账号/栏目、选题顺序、用户批准哪一版、失败尝试和恢复入口。Codex 擅长创作，CreatorOS 把生产变成可查询、可验收的业务任务。未来如果调研、反馈和管理没有带来收益，就应收缩业务层，而不是为了 Agent 的名义继续加模块。

追问证据：展示一篇 ContentRun 的输入快照、两次 Attempt 和批准 digest。

2. 为什么从知乎分身转成 Skill 栏目？原项目是不是白做了？

原路线验证了“作者与热点匹配”和远程生成服务的组合，但真人分身矩阵的公开运营需要解决身份、账号和授权等现实约束。自有知识栏目可以复用生产方法，并让后续效果反馈有真实实验环境。画像路由、异步客户端、SelectionPlan 仍保留为实验能力；共同学习到的结构化契约、服务边界与执行记录继续被主线复用。

3. 这到底是 Workflow 还是 Agent？

两者都有。CLI 通用 Loop 由模型根据工具结果决定下一步；Studio 目前由受限模型解析用户意图，计划执行和生产恢复由确定性服务负责；Codex 内部自主完成生产。当前动态运营规划还有限，所以最准确是“Workflow + Agent 混合架构”，而不是全自治运营已经完成。

理由：选哪个题、如何解释反馈有不确定性；“批准的是哪张图”和“是否重复创建任务”需要稳定规则。

4. 为什么自己写 Runtime，没直接用框架？

早期目标包括学习：通过实际痛点理解模型适配、工具校验、流式事件、上下文与持久化的边界。业务服务没有绑定某个框架的内部状态对象，后续可以替换外层编排。代价是需要自己补测试和恢复能力，因此我们没有追求复刻完整 Coding Agent。Pi 用作架构参照，不是复制实现。

别过度承诺：有 Provider Protocol 只说明设计上可替换，不表示所有模型已适配。

5. 多原型路由为什么用 Max，不用平均？

作者可能具有多个相距很远的领域。平均向量会把细分专长稀释；取热点与作者各原型的最大相似度，可以由最相关领域代表这次匹配，同时返回命中原型解释原因。Max 对多原型数量和宽泛标签可能有偏好，因此需要样本检验。当前只启用 domain，不声称人格双通道已经带来提升。

6. Skill、Tool、MCP 有什么区别？

Tool 是可执行能力与输入输出契约；Skill 是如何组织能力完成一类任务的指导；MCP 是把能力提供给不同宿主的协议。当前 SkillLoader 负责发现与按需读取，本地 Tool Registry 负责执行，Codex 通过 CLI 适配器接入，尚没有 MCP Server。要标准化时优先暴露边界清晰的研究/生产服务，而不是把所有内部类直接变成工具。

7. 长期记忆是怎么做的？

现阶段有 CLI 消息快照、累计压缩摘要、运营数据库与 Codex thread。它们保存事实，但尚未构成完整的反馈提取与自动召回系统。最小后续方案是按账号/栏目保存人工反馈与可追溯偏好，生产前组装简报，再通过有无记忆的成对任务验证效果。存储是记忆系统的基础，不等于全部。

8. 既然 API 返回 usage，为什么还估算 token？

usage 是请求结束后已处理输入的真实消耗；发出下一次请求前，工具结果和新消息可能已经变化，所以仍需预检。当前本地估算用于触发预算警告与压缩，usage 用于事后观察。模型窗口是配置能力，usage 是本次成本，它们是不同量。下一步可做估算误差校准和超大单轮处理。

9. Context Compaction 会不会丢信息？原始结果还能找吗？

摘要必然有信息损失风险，所以完整 Session 保留，模型请求只使用摘要与近期完整回合。大型工具结果投影包含 result_ref，可分页读原文。第二次压缩更新一份累计摘要。现在检查的是 Markdown 标题等结构，还没有语义保真评测；可以用“压缩前后是否仍遵守关键约束”做任务测试。

10. 你如何确保用户批准的是他看到的版本？

批准请求带所见 version、Revision ID 和 artifact digest，服务重新验算产物摘要后再迁移状态。旧页面、返工后旧版本或图片被替换都会导致冲突。version 防并发状态变化，Revision 区分内容版本，digest 绑定具体内容，三个检查解决不同问题。

11. 事务回滚能撤回图片生成吗？如何理解 exactly-once？

不能。数据库事务可以保证队列更新、执行状态和相关事件的原子写入；无法撤回已经完成的外部模型调用和费用。系统使用幂等业务键、尝试记录、owner 检查和可恢复 thread 降低重复执行风险，不承诺跨数据库和外部 Agent 的严格 exactly-once。恢复时应区分重新调用与复用已有产物。

12. SSE、后台线程和模型流式输出是一回事吗？

不是。后台线程使 HTTP 不必等待整篇生产；Studio SSE 是把状态事件送给浏览器；模型 SSE 是模型把文本/工具参数分段送给 Provider；Codex CLI 则向 CreatorOS 输出 JSONL。它们分别解决执行占用、页面观察与增量传输问题。当前状态心跳也不是精确的图片完成百分比。

13. SQLite 会不会很 toy？为什么有 SQLAlchemy 和 Alembic？

当前是本地单写运营工具，SQLite 部署简单，足以验证事务、状态恢复与版本冲突。SQLAlchemy 管数据访问，Alembic 管 schema 演进。业务对 Repository 编程方便未来迁移；但 PostgreSQL 是否兼容需要实际跑迁移和集成测试，不能因为用了 ORM 就说迁移已经完成。

14. Agent Eval 怎样避免“模型说完成了就算成功”？

固定初始环境与任务目标，结束后直接检验数据库和文件约束。例如用户只要求调整某一栏目，正确结果是目标顺序正确且其他栏目未变；遇到歧义应澄清并不写数据。轨迹用于解释失败和成本，不要求所有成功路径完全相同。恢复任务单独注入故障，并区分低成本受控验证与真实外部模型验收。

15. 你现在最有把握的亮点是什么？

是把概率性的模型调用接入可检查的业务生命周期。用户表达经过受限结构化解析和 Preview；生产使用独立 thread、Run/Revision/Attempt 和不可混淆的批准对象；上下文对工作副本做压缩，完整记录仍可查。下一步最该拿出的结果是任务成功与失败归因，而不是更多框架名称。

五句话，检查自己是否真的理解。

  • 我能不看代码，画出 Studio 指令、内容生产、CLI Loop 三条路径。
  • 我能用两位作者和三个热点，手算一次 Max Similarity 与 Top-K。
  • 我能解释 Session、摘要、数据库和 Codex thread 各保存什么。
  • 我能用一次断线和一次改封面，区分 Attempt 与 Revision。
  • 我能给一个用户任务写出可机器验证的成功条件，而不是只读最终回复。
