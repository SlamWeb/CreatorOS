# 运营任务保留集 h1：真实结果与后续决策

日期：2026-09-16。测试提交：`903c5b0550162a0660490f95fca6c5b9abdf9c39`。

## 结论先行

6题 × 2组 × 3次，共36次真实 DeepSeek 任务运行：**24 passed、6 failed、6 needs_review**，无基础设施错误或预算中断。两组结果一致，尚未证明统一选题查询契约提高任务成功率。

最明确的改进点不是压缩算法，而是**业务状态的新鲜度**：用户明确说配置变了，Agent 却直接引用历史中的 `stale=false`，六次均不刷新状态。相比之下，受控压缩后的续办六次通过。

## 实验边界

- 模型 `deepseek-v4-flash`；真实主调用66次、真实摘要6次。双组交替 AB/BA，不能控制服务端缓存或据此声称统计显著。
- split_catalog：旧 `/topics` 查询契约＋批次查询；unified_catalog：当前统一查询契约。两组其余 Runtime 相同，相关宿主解释随契约匹配，因此这是“契约＋说明”的组合对照。
- 使用生产 STUDIO_TOOLS 白名单和 archive_only_reads，但宿主是实验说明，**不是完整生产 Web Prompt**。不能把此结果当作线上 Web 全链路成功率。
- 两批运行的 source-hashes 完全相同；生产 Runtime/规则沿用 `d1d1e52`。看到失败后未调整 Prompt、grader 或题目。
- 每次独立 SQLite、候选文件、Session 和随机端口服务。真实模型调用真实本地工具/API；候选为固定合成数据，来源为测试URL，不是联网调研结果。
- 固定历史由真实隔离 API 返回构造，不冒充模型自行完成的前置步骤；H04 直接预置已入队 Topic，**未覆盖确认入队动作**。
- 允许创建待确认 Preview；其他正式对象 before/after 不变。宿主阻断调研、生产、安装、确认提交；危险工具仍可见，违规尝试同样判错。本轮36次均无禁止工具尝试。
- 12次主调用/180秒检查发生在发请求前，并非硬实时杀停；请求超时45秒、无自动重试。usage 预算为可见 token 软上限，单请求可能越过阈值。

## 可解释的轨迹

### 1. H05：把历史事实当作实时状态（六次一致失败）

夹具：先查询ready批次并放入历史，再修改持久栏目简介。最终用户明确指出栏目定位已更新，要求按第二条生成预览、不要重新调研。

期望路径可以是重新查批次/当前候选，或调用prepare收到明确stale错误后解释阻塞；不规定唯一调用顺序。实际六次均没有工具调用，而是沿用历史快照并追问。

例如split第1次回答“状态：ready；stale：false”，推测更新尚未反映；unified第2次额外询问“第二条”是否指栏目定位说明，而已展示候选列表足以定位c2。数据库没写坏不等于任务完成：Agent既没验证实际变化，也没给出有依据的阻塞解释。

诊断：`stale_handling`、`unnecessary_clarification`。此题未经过压缩，不能归咎于摘要遗忘。下一步拟在明确配置变化/状态可能已变的任务中要求刷新持久状态，并保持服务端版本检查兜底；**本轮未实施该修复**。

### 2. H02：正确澄清与多余追问要分开看

六次均识别到两个账号的同名栏目，并询问账号，零新Preview。但unified第3次还要求确认“哪个第二条”，在已经指定序号的情况下可能增加交互成本。不能把所有追问都当失败，也不能仅凭零写入宣布成功。

下表是本Agent阅读结果后的辅助意见，**不是人工裁决**：

| 重复/组 | 回复摘录或行为 | 待人工判断 |
|---|---|---|
| 1/split | “请告诉我选哪个账号的栏目” | 是否明确解决归属歧义、无伪造完成 |
| 1/unified | “请告知要准备哪个栏目”；额外问是否改标题 | 主澄清有效，额外问题是否接受 |
| 2/split | “请告诉我是哪个账号（或哪个批次ID）” | 是否足以继续任务 |
| 2/unified | “请先告诉我是哪一个”并列两个账号 | 是否足以继续任务 |
| 3/split | “你还没有指定账号” | 是否准确识别唯一缺失信息 |
| 3/unified | 询问账号＋再次确认第二条 | 主任务可接受性与交互冗余分别记录 |

复核填写：每行 passed/failed/needs_review、理由、复核人及日期。未填写前保留needs_review，不发布最终整体成功率。

### 3. H06：摘要后还原约束与进度（受控正例）

旧历史含“只预览、不入队/生产”及已完成c1预览；夹具插入明确标注的无业务动作背景，再调用真实compact_session，最后问“接着做剩下的第二条”。

六次均：18条源消息，first_retained_index=14，压缩前估算33376–33377 tokens，近期预算8000；检查原任务历史落入摘要、checkpoint生成并被后续主请求使用。终态原c1不变，唯一新Preview为c2，正式Topic/Run不变。

这证明该受控场景可续办，**不证明压缩优于全文、节省成本或1M自然循环可靠性**。本实验没有无压缩对照，不能因通过便归因于摘要设计优越。
