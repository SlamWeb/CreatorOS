## 为什么分层

- 24 个账号 Agent 场景：用户意图、作用域、上下文、工具选择、状态与交付。
- 14 个 Skill 工作台场景：安装、浏览、四模式提炼、编辑、审核入库、融合及冲突。
- 6 个业务可靠性场景：并发版本、转移、删除、执行所有权与磁盘故障。
- 6 个真实 Codex 交付场景：单／双 Skill、新题材迁移、返工、离线恢复与实际看图讨论。

这是 50 个不同任务场景，而非 50 次通用能力测量。E09 有 failed／unknown，B06 有 diagnostic／authoritative，因此完整定义是 **52 个首尝试执行槽**。内部的几十条检查不另算题数，同一题后续重复也不增加覆盖数。

正常路径使用真实业务服务、SQLite／文件、原 SPA；正常 LLM 行为不由 Mock 替换。隔离夹具是本地真实记录，不是伪造工具结果。声明故障题只在指定位置注入，不能把它们算成供应商随机可用性或内容质量成绩。

## 每题如何判分

1. execution_evidence：真实用户入口、终态、每个公开请求／工具／SDK item、前后状态及页面证据齐全；缺证据不能通过。
2. business_state：授权增量、归属、集合／顺序、回执、输入快照和状态一致；真实数据库全行、文件 hash 与权威 receipt 为依据。
3. delivery_semantics：回答与实际事实一致，准确区分完成／提交／失败／未知、数量与来源；模型原文和宿主链接交付分别保存。链接必须在浏览器真实点击并核对资源，不仅匹配文本。
4. content_quality：图像需实际解码、naturalWidth>0；词义、双语、故事连续性、角色／模板与迁移能力按该题固定目标另评，合法 artifact 不等于内容好。

前三层全 passed 才算完整任务通过，needs_review／evidence_missing 不偷计成功。生产题的内容质量另列，不把文件检查与审美／教学评分混成一项。独立阅读或固定评估者给结构化结论并保存依据，用真实坏例先校准；没有评估则明确待评估，不用固定中文词串代替语义理解。强制宿主探针与模型主动动作分开，不要求唯一工具顺序。

## 基线、修复和重复

先接线并验证 grader 正／负例，再冻结题目、oracle、采集协议、模型参数和源文件 hash。首尝试完整跑一轮，retries=0，所有环境错误、失败、证据缺失留账，不边跑边修。统一归因修复后跑同冻结题集全量回归。

报告分别给出四层的 passed／failed／needs_review／evidence_missing／not_run 及分母，正常路径与声明故障分列。后续重复使用新 run_id、repeat_index 并保留首尝试；预登记重复方案，不挑成功答案，也不声称公开阶段验收是盲测。

DeepSeek 与 Codex 的 usage 分开，缺值为 null，缓存与 last_request／thread_cumulative 口径明确；同步报告耗时、实际新图和模型／生图调用数。只有同题、同判分器／采集协议、同模型配置才比较迭代前后。旧 6/13 与 10/13 是版本不同的程序分数，不能写成严格完整任务成功率从 46% 提升到 77%。
