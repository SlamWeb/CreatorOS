# Eval 看板讨论记录

状态：需求讨论中，尚未确认完整设计或开始实现。

## 已对齐

- 看板帮助用户理解每轮改动、测试进展、结果和历史变化；测试选择、开发与执行主要由 Codex 协助。
- 以更新轮次组织记录，一轮可以关联多次测试。
- 每次测试运行独立留档，轮次首页对每个专项分别显示其最近一次运行，可切换查看更早运行；代码或配置变更记为新的更新轮次。部分选题运行应标为部分，不能当作整个套件完成。
- 测试从基础测试、专项评测、完整链路评测三个层次理解，安全边界贯穿各层。
- 工具调用允许多种合理完成方式；同时比较调用次数、Token 和耗时。
- 改动端可以自主增加临时测试，结果保留在轮次中但不自动成为首页常设项目；值得长期防回归的用例经整理后加入统一维护的正式专项集或回归集。
- 改动先做相关专项，再在合并前做必要跨链路检查；更广回归依据影响范围、重要版本及基线需求安排，不把所有改动都强制全量运行。
- 常规全量回归以 DeepSeek、工具调用及可控链路为主，尽量运行全部符合条件的题；需要较慢 Codex session、生图或视频等资源的题放入更重的完整回归。实际准入需核实任务依赖、费用和副作用，并记录未运行项；具体清单和运行成本待盘点。
- 常规全量与完整回归分别维护可版本化的题目清单；新增题按实际依赖和运行成本归类，轮次记录实际运行内容。
- 评测体系作为项目 Harness 的公共能力提供方，为开发端提供复用的测试与 Eval、使用规则及统一结果记录；开发端可自行创建临时测试，也可申请运行公共评测。
- 项目定义的必要测试不得悄悄省略；因成本、环境等未执行时须记录未验证及原因，不能算通过。
- 开发端声明改动范围与验证目标，评测体系按维护的规则列出必要和建议测试；开发端可补充测试，必要项未运行时显示原因。
- 正式评测无论成功失败，未合并前也展示在主看板并标明开发中或已合并；临时测试保留在各自轮次，不自动铺到主看板。
- 正式评测默认使用独立测试数据和输出目录，保留结果与必要证据；明确标注真实模型、外部服务和测试替身，不改动真实草稿、任务及历史素材。
- 真实使用中发现的异常应评估是否能转化为脱敏、可复现的回归用例；值得长期防回归的案例加入对应测试或评测集。
- 根 AGENTS.md 提供简短必读规则并链接详细评测使用文档；实际运行工具负责执行和结果记录。开发端完成改动时说明改动内容、正式测试、结果和必要测试未运行原因。不同工作树需要取得相应版本才能使用更新后的规则。
- 结果默认对比上一轮，也可选择之前的版本。可比性不足时须说明，不伪造涨跌。
- 每轮展示自身测试范围；跨轮直接比较以双方共同执行且可比较的题目为基础，显示共同题数并标明模型、题目和评分标准等差异。
- 首页以更新记录和选中轮次的结果为主线；不需要长期趋势作为首页重点。各版本可回看，并可自由选择历史版本比较。
- 轮次详情依次展示改动、对比结果、测试进展和值得关注的问题；专项和完整链路优先展示，基础测试默认收起、失败时明显提醒，安全边界单独标明。
- 安全关键项失败不得被平均分抵消；必要测试未执行或证据不足时分别显示未验证或待复核；本轮冻结清单中的必要专项和必要链路完成后再形成整体结论，非必要的完整回归标为不适用，Token 和耗时变化独立展示并结合改动目标判断。
- 评测详情先展示题目列表；单题详情默认展示用户任务、结果、对比变化及判断依据，实际工具调用和原始证据可展开查看。失败与证据不足分别说明。
- 每版应能回溯并支持回滚：回滚代码和配置，保留用户数据及所有测试记录。
- 版本记录覆盖代码、提示词、工具定义、相关配置、模型及参数、依赖和必要服务配置，以及题集和评分版本；密钥不进入版本记录，未提交改动也需可恢复。
- 回滚默认暂停接收新任务，等待运行中任务完成后切换并验证，再恢复接收；不自动取消或重复执行任务。长时间未结束或版本与现有数据不兼容时先停下来说明。
- 可重新设计并重建现有 Eval 前后端；历史评测证据和版本回溯需求仍需保护。
- 看板视觉设计不必沿用现有页面和 DESIGN.md；用布局和信息层级表达，减少装饰性和解释性文案。
