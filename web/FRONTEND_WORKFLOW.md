# CreatorOS 前端工作流

适用于页面、样式、交互、组件、前端 API 接线和视觉资产。先读根级 AGENTS.md、本文件、最近 SPEC；本文件是协作门槛，不代表所有测试已经实现。

核心原则：**截图证明外观，操作与状态断言证明行为；两者不能互相替代。** 不把“页面打开了 / 无报错 / build 成功”写成“功能验收通过”。

## 1. 工具怎么分工

| 层 | 当前采用 | 使用边界 |
| --- | --- | --- |
| 应用 | React + TypeScript + Vite；Python/FastAPI | 不为换皮迁移 Next.js；业务状态仍以现有服务为准 |
| UI | 现有 CSS 与组件，逐步整理设计 tokens | Tailwind/shadcn 可单独评估，不批量安装或整站替换；组件库不能决定产品设计 |
| 探索操作 | 当前可用浏览器自动化工具 | 实际点击、输入、导航、刷新；遵守宿主浏览器工具规则，不另开绕过工具的控制通道 |
| 诊断 | 浏览器日志、网络观察、必要时性能记录 | DevTools MCP 是可选诊断手段，不是必须安装的前提；工具缺失时明确替代证据 |
| 可重复回归 | 仓库已有 Playwright Test | 自动断言用户可见状态与业务状态；必要时建立受审查的截图基线 |

不把 Playwright CLI、浏览器执行 Skill、Playwright Test 当成同一个东西：探索工具帮助发现问题；测试脚本负责稳定复现。使用组件库仍需验收焦点、键盘、受控状态和业务接线。

## 2. 开工前：先把要做的事写清楚

在最近 SPEC 写一页以内的本次设计说明：

- 用户目标：例如“为自己的栏目选两条候选，并知道它们还没有开始生产”。
- 入口、主动作、完成后的落点、返回方式；哪些现有行为不改。
- 影响页面/组件/API；状态由服务器、URL 或页面草稿中的哪一处持有。
- 空、加载、成功、失败、过期、进行中、只读状态分别显示什么。
- 3–5 条 Given / When / Then 验收用例，写出应发生和不应发生的事。
- 外观改动前留基线截图；行为改动前跑关联测试。原有失败与本次新增失败分开记录。

未知较多先做一个代表页面，不先重写整站。大幅视觉重设计先给两种方向或一个低保真布局，与用户确认后再扩散；已确认范围内的小修无需反复询问。

## 3. 设计：从运营任务出发，不从卡片堆砌出发

- 当前方向为用户确认的 B：浅色、石墨正文、少量蓝/橙/绿/粉点缀；栏目页为视觉参照，全站共用主题变量。
- 用内容层级、字体、间距、布局和真实产物建立辨识度；避免无目的渐变、发光、玻璃卡片和无意义 KPI。
- 一屏能回答：我在管理谁、现在什么状态、下一步能做什么、做完去哪里。
- Creator → 栏目 → 候选 → 队列 → Run → 产物，名称和返回路径稳定；不要把安装、绑定、调研、入队、生产、批准混成一个“开始”。
- 默认突出当前任务。技术 ID、Token、Trace 等放在可展开详情，不删除调试入口。
- 第一页也必须有内容策略：空账号引导创建；已有账号显示可运营对象；不能只给一个空聊天框。
- 统一少量颜色、字体层级、间距、圆角和状态样式；先限定作用域再调整 tokens，禁止全局 input/button 样式误伤 checkbox、弹窗等。
- 文案必须符合实际能力，例如“默认 Skill，可更换”而不是“固定 Skill”；未完成不能写已完成，批准不等于发布。

## 4. 实现：先做一个能走通的切片

先接真实 API 和状态，再完成样式；保留服务、DTO、权限/审批与幂等边界。需要改变业务含义时单独说明，不把重构藏在视觉改动中。

每个交互控件检查：触发条件、提交数据、忙时行为、失败反馈、成功状态、是否可撤销或回退。删除无功能按钮，或明确禁用原因，不使用假成功 Toast。

异步与草稿规则：

- 切换栏目/批次后，旧请求不能覆盖新对象；旧选择不能以同名 ID 套到新批次。
- 重复点击不能重复生产；结果未知先查询，不能自动重发付费/写入动作。
- 关闭页面不等于取消后台任务；返回时读取同一任务，不重新提交。
- 明确哪些草稿离开/刷新会丢失；关键编辑要保存或提示，不暗示已经持久化。
- 确认绑定用户所见版本；发生冲突重新展示，不能刷新凭证后偷偷确认。
- 键盘 Tab/Enter/Escape、中文输入法 composition、焦点进入/离开弹窗、原生禁用语义都要检查。

## 5. 验收：行为与视觉双轨，证据必须匹配结论

### 行为轨

每个受影响流程都要真实操作，不只读 DOM 或检查按钮存在。至少覆盖一条主路径、一条失败路径、一条返回/刷新路径；涉及异步/确认时加竞争路径。

| 场景 | 必须验证的结果 |
| --- | --- |
| 创建 Creator / 栏目 | 显示真实新对象；保存失败不显示成功；刷新仍存在 |
| Skill 安装/绑定 | 安装不等于绑定；绑定改变的是目标栏目；旧 Run 不被改写 |
| 调研候选 | 请求进入后台；返回能找到同一批次；候选不直接进队列 |
| 选择候选 | 单选/多选/全选/取消、标题/切入点修改、调序与来源保持一致 |
| Preview/确认 | Preview 零入队；确认才写；双击、旧版本与重复候选不重复写 |
| 配置变化 | 调研中/就绪后/Preview 后改变栏目或 Skill，按约定刷新或阻止旧结果 |
| Run/验收 | 离开与回来不重启生产；故障可见；批准明确为未发布 |
| Agent 对话 | 工具输出与 UI/持久化状态相符，不凭模型口头答复判断成功 |

关键操作至少检查“UI + API/持久化状态”两类证据。例如点击 Preview 后不仅检查弹窗，还检查 Topic 数没变；确认后检查顺序/brief，刷新再检查。

自动测试优先用 role/label 定位和自动等待断言，不依赖易变索引、固定 sleep。数据在独立 SQLite/产物目录，不能顺手修改正式运营账号。

真实/受控测试分工：

- 交互状态、断网、延迟、过期版本等用确定性数据或故障注入；必须标为受控测试。
- 改模型/API 接线时，低频真实服务验证；不用 Mock 的成功证明真实服务可用。
- 纯布局修改不重复消耗生图/模型额度；复用标注为测试的既有真实工件。
- 发布、生图等副作用按本轮授权范围执行，测试脚本不得意外触发。

### 视觉轨

- 用真实渲染截图检查受影响状态，不只首页。至少桌面 1440×900、手机 390×844；弹窗、长标题、空态、错误态、数据密集态按影响面补测。
- 检查层级、对比度、截断、按钮碰撞、焦点可见性、滚动容器、遮挡、图片裁切和加载位移；不能只断言无横向溢出。
- 生图资产必须放进真实布局后验收；单看素材好看不算通过。
- 对稳定区域逐步增加 `toHaveScreenshot`。固定浏览器/字体/视口与测试数据；动态时间等只遮蔽确实无关部分。禁止遮住交互主体来让测试通过。
- 首次基线需人工看图，用户确认的设计才是审美锚点；diff 不能自动判定“更漂亮”，也不能直接更新基线消除失败。

## 6. 自我迭代：发现 → 复现 → 修复 → 原路径重跑

在最近 SPEC 记录问题，不再建独立的大型缺陷系统：

| ID | 用户动作/前置状态 | 预期 vs 实际 | 原因 | 修复 | 回归证据 |
| --- | --- | --- | --- | --- | --- |
| UI-001 | 候选全选后查看标题 | 标题正常换行，实际挤成单列 | 全局 input 宽度影响 checkbox | 独立尺寸及作用域 | 全选/单选截图 + 布局断言 |

修复后必须重新执行触发问题的步骤，并检查相邻状态；新增可稳定复现的行为 bug，应加入回归测试。不能仅拍修复后静态图。同一问题连续两次修复无效，停止试 CSS 参数，查 DOM/computed style、请求与状态归属。

门槛：阻断任务、错误对象写入、重复付费、数据丢失、不可返回的问题未解决不得标记完成。次要视觉问题明确列出，不伪称零问题。用户报告漏测时，补的是测试用例与工作流，不仅是当次补丁。

## 7. 当前可执行入口与缺口

仓库根目录 PowerShell：

```powershell
$env:CREATOROS_PYTHON = 'D:\Anaconda4.7g\envs\deepcode\python.exe'
npm --prefix web run typecheck
npm --prefix web run build
npm --prefix web run e2e
```

- `web/playwright.config.ts` 使用隔离临时目录和 8877 端口；不复用现有服务，先检查端口，不杀用户进程。Chrome/依赖不可用时先报告，不静默安装。
- `web/e2e/studio-workflow.spec.ts` 已有创建、确认冲突、受控生产/返工/批准、刷新及移动端流程。受控 Producer 不是 Codex 真生产证明。
- 目前没有截图差异基线；调研候选的勾选、编辑、重选、调序已有 E2E。全站主题回归检查首页、账号、运行、Agent 的桌面与手机布局，仍需按每轮影响面补验收。
- 浏览器探索与 Playwright Test 回归互补。当前宿主限制浏览器控制工具时遵守限制；不能运行的测试记录为未运行，并列替代证据，不能宣称等价覆盖。
- 纯文档轮只检查文档路径、命令和 Git diff，不为了凑验收启动服务/调用模型。

## 8. 生图怎样参与前端

生图可服务两件事：①做视觉方向稿，帮助选定构图/氛围；②制作真正上线的插画资产。两者必须分开标记。

适合：品牌概念插画、首次使用引导、空态插画、栏目封面、公开展示页主视觉。运营页优先展示真实内容产物；插画不能挤走关键任务。

不适合：把整页 UI 当作一张图、图片里的可点击按钮、动态数字、表格正文、不可选择的文字；这些必须由 HTML/CSS 真实实现。常规图标优先现有 SVG 图标系统，不逐个生图。

一次只做一个代表资产：先定使用位置/尺寸比例/留白区，再给参考图和色彩约束，生成后在实际组件中检查桌面/手机裁切、文字对比和文件大小；方向被认可后再扩展同系列。视觉草稿不要求先接付费 API 到产品里。

提示词骨架（方向需先与用户确认）：

> 为 CreatorOS 的「首次创建内容栏目」页面生成一张品牌插画，不是网页截图。表现用户像主编一样组织多个内容栏目，AI 是协作生产者。横向 3:2，左侧保留干净留白供网页文字覆盖。风格、主色与参考图一致；不出现文字、按钮、图表、假数据、第三方 Logo；主体在手机裁切时仍清楚。输出独立插画，不替代真实 UI。

交付资产时记录用途、生成提示词、参考来源/使用权、实际可确认的模型、尺寸及版本。模型未知就标未知，不能把工具成功等同于用了用户指定的新模型。通过审核的素材放 `web/src/assets/`，实验稿和 QA 图放忽略目录；命名可理解、提供 alt 或装饰性空 alt、压缩并预留宽高。

## 9. 完成前的交付格式

1. 改了什么，以及刻意没改什么。
2. 实际走过的操作路径和状态断言；命令、结果、隔离环境。
3. 已看过的截图状态/视口；自动回归覆盖与未覆盖项。
4. 本轮发现了什么，如何复现和防止再发生；阻塞未解决就不能说完成。
5. 更新 SPEC，检查 staged/unstaged diff，只提交相关文件，commit/push；必要时给用户一条最短验收路径。
